## 3. Архитектурные решения

**Страница читает `company_profiles` напрямую, а не через `resolveCompanyContext`.**
Рассмотрено прямо, поскольку неоднозначность была реальной: `resolveCompanyContext` (Stage 5) уже делает почти тот же запрос для ветки "user". Отклонено по трём причинам: (а) эта функция принимает `Identity` — абстракцию про гостя/пользователя, не нужную здесь (страница защищена layout'ом, гостя тут никогда не будет); (б) она возвращает форму, заточенную под сборку промпта (`CompanyContext` без `id`, без ограничений длины) — не форму, пригодную для редактирования; (в) записи в таблицу эта функция не делает вообще, значит write-путь в любом случае пришлось бы писать заново — согласованнее, когда read и write одной страницы используют один и тот же прямой доступ через один и тот же существующий клиент (`lib/supabase/server.ts`), а не смешивать "чтение через pipeline-хелпер" и "запись напрямую". `resolveCompanyContext` не изменена и не тронута ни байтом.

**`GuestCompanyProfileDraft` не импортирован напрямую — форма полей воспроизведена локально с тем же составом.**
Тоже рассмотрено явно. Импорт этого типа из `lib/guest-session/` в форму профиля работал бы технически, но добавил бы полю `id` (которого нет у гостевого черновика) поверх типа, названного и предназначенного для другого домена. Сохранён тот же набор полей, те же имена — именно то намеренное совпадение, что уже использует Stage 11 для записи в ту же таблицу — но как собственный интерфейс формы, а не переиспользованный тип с чужим именем и неполным составом полей.

**Единственная схема валидации — в `actions.ts`, ничего в клиенте.**
Клиентская форма использует только нативные HTML-ограничения (`required`, `maxLength`) для немедленной подсказки при вводе — не как источник истины, а как UX-удобство. Авторитетная проверка одна — zod-схема в server action, тот же принцип, что уже применяется в `/api/generate` (Stage 5) и в `ToolRunner`'s клиентской non-authoritative проверке (Stage 6).

**Создание/обновление в одном action, ветвление по наличию `id` из формы, апдейт — по `id`, не по `user_id`.**
`company_profiles` намеренно допускает несколько строк на пользователя (Stage 3, под будущие агентские сценарии) — обновление по `user_id` без уточнения конкретной строки задело бы разом все профили пользователя, если их окажется больше одного. `id` берётся из значения, только что прочитанного самой страницей (skрытое поле формы), не из отдельного повторного запроса "существует ли профиль" — избежано дублирование уже выполненного чтения.

**Переиспользован `FieldWrapper` (Stage 6, `components/tools/fields/`) без единого изменения в нём.**
Прямое исполнение инструкции ("именно так, как было сделано с SearchBar в Stage 10"). Компонент уже был чисто презентационным (label/required/helpText/error), без зависимости от системы `config_schema` — единственный компонент формы, который получилось переиспользовать буквально как есть, без добавления даже опциональных пропов (в отличие от `SearchBar` в Stage 10, которому пришлось добавить два опциональных пропа).

**Не переиспользованы `TextField`/`TextareaField`/реестр полей `FieldRenderer` (Stage 6).**
Рассмотрено и отклонено: те компоненты — контролируемые (`value`+`onChange`, завязаны на `FieldConfig`-объекты из динамической, БД-заданной схемы инструмента). Форма профиля — неконтролируемая (`name`+`defaultValue`, отправка через `<form action={serverAction}>`), тот же паттерн, что уже используют `login`/`register` (Stage 2). Применение контролируемых компонентов означало бы подгонять чужой контракт под несовпадающую по природе задачу — то самое "новая форма, потому что так красивее" наоборот: здесь пришлось бы **искусственно усложнить**, чтобы формально переиспользовать компоненты, для которых этот сценарий не создавался.

**`revalidatePath("/profile")` — первое использование этого примитива в проекте, но не новая архитектурная сущность.**
Это встроенный примитив Next.js App Router, не абстракция, придуманная для этой стадии. Нужен, потому что `login`/`register` (единственный прежний прецедент Server Action + отображаемые Server Component-данные) всегда делали `redirect()` после успеха, что само по себе форсирует свежий рендер — эта форма остаётся на странице (показывает "Saved." инлайн), так что без явного `revalidatePath` последующая перезагрузка могла бы показать нессвежие данные, а следующее сохранение — не увидеть `id`, если бы уже был.

**Новый API-маршрут не создан.**
Проверено по инструкции: "если достаточно server action — использовать её" — её оказалось достаточно, отдельный `/api/profile` не понадобился.

**Проверка "не появился ли второй способ работы с `company_profiles`".**
Явно выполнена (см. §9) — все четыре места доступа к таблице (`resolveCompanyContext`, merge-эндпоинт Stage 11, новые `actions.ts`/`page.tsx`) используют один и тот же путь: прямой запрос через существующий Supabase-клиент, под защитой RLS. Ни разу не создана обёртка/репозиторий/сервис поверх этого — именно то, что задание explicitly запрещает (`ProfileService`, `CompanyManager`, `ProfileRepository`, `lib/profile`).

## 7. Потенциальные риски первой сборки

Только реальные, без формальных пунктов:

1. **`zod`'s `.optional()` на пустой строке.** Поля вроде `niche` отправляются как пустая строка, если не заполнены (HTML-форма всегда шлёт строку, не `undefined`) — `emptyToUndefined()` в `actions.ts` явно преобразует пустую строку в `undefined` до валидации именно ради этого; логика проверена вручную построчно, но не прогонялась через реальный `zod`.
2. **`useFormState`'s начальный рендер до первого сабмита.** Форма показывает `initialProfile` через `defaultValue` — если Next.js/React в конкретной установленной версии обработает `useFormState`'s исходное состояние иначе, чем ожидается (маловероятно, паттерн идентичен уже "проверенному" в Stage 2), это не проверялось именно с этой формой.

## 8. Компромиссные решения

Одно, явное: **`logo_url` не выведен в форму.** Колонка существует (Stage 3), но загрузка файла требует инфраструктуры (Supabase Storage), которой в проекте пока нет ни в каком виде — задание Stage 12 ограничивает объём "уже существующими полями таблицы" и нигде не просит файловую загрузку. Это не техдолг: колонка остаётся в схеме нетронутой, ничего не блокирует её появление в форме, когда (и если) в проект добавится Storage-инфраструктура.

## 10. Почему Stage 13 можно начинать без переписывания Stage 12

Stage 13 (по исходному плану — usage-лимиты в UI, Billing/Settings) не имеет функциональной зависимости от того, как именно устроена страница `/profile`: она читает лимиты из `plan_limits`/`usage_counters` (Stage 5), а не из `company_profiles`. Единственное, что Stage 13 могло бы унаследовать от этой стадии — сам паттерн "Server Component читает + Client Component с `useFormState` сохраняет через Server Action", уже дважды подтверждённый (Stage 2, Stage 12) как рабочий, воспроизводимый подход для любой будущей формы в `(auth)`-группе — не обязательство, а готовый, проверенный шаблон, которым можно воспользоваться, если он подойдёт.
