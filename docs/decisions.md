# Лист решений

Короткая фиксация решений, от которых зависят следующие фазы (схема БД,
монетизация, UX). Это не процесс ADR: один абзац на решение — что выбрано,
почему и во что обойдётся смена. Решения со статусом «открыто» ждут
владельца продукта; до указанной фазы их можно не закрывать.

## 1. Владение данными — пользователь (без workspace)

**Решение.** Каждая строка принадлежит одному пользователю: `user_id`, а
у гостя — `guest_session_id` (`generations`, `company_profiles`,
`usage_counters`). RLS проверяет `auth.uid() = user_id`. Команд,
организаций и приглашений нет; при регистрации гостевые данные
переносятся на пользователя (`/api/session/merge`).

**Почему.** Продукт для малого бизнеса, где работает один человек. Так
устроены все таблицы с Stage 3, и RLS остаётся простой.

**Цена смены.** Тарифу Enterprise в архитектуре обещана «команда (задел на
будущее)». Если это понадобится, придётся:
- добавить `workspaces` и `workspace_members`;
- перенести владение с `user_id` на `workspace_id` во всех таблицах;
- переписать политики RLS.

Это миграция данных, а не новая фича. Если команды нужны уже в MVP,
решать надо до Ф2, пока реальных данных мало.

## 2. Оплата — Stripe

**Решение (владелец, приёмка Ф1).** Stripe. Merchant of Record (Paddle,
Lemon Squeezy) можно подключить позже без изменения архитектуры:
`subscriptions.provider_ref` не привязан к провайдеру. Ниже — разбор, на
котором решение принималось.

**Как было.** В архитектуре (§18) указан Stripe. В схеме уже есть
`subscriptions.status` и `provider_ref`: поле не привязано к Stripe и
подходит любому провайдеру. Кода оплаты нет — это Ф6.

**Выбор**, который меняет Ф6 и стоимость:
- **Stripe** — продавцом выступаете вы. Регистрация и уплата налогов с
  продаж (VAT/GST/sales tax) в странах покупателей — на вас; Stripe Tax
  их только рассчитывает. Комиссия ниже. Stripe доступен не во всех
  странах: проверьте для страны, где зарегистрирован ваш бизнес.
- **Merchant of Record** (Paddle, Lemon Squeezy и аналоги) — продавцом
  выступает провайдер: он собирает и платит налоги по всему миру и
  выставляет счета. Комиссия заметно выше, но для solo-разработчика,
  продающего в разные страны, налоговая часть почти исчезает.

**Рекомендация.** Если покупатели будут из многих стран (особенно ЕС) и
у вас нет бухгалтера — Merchant of Record. Если продаёте в основном в
одной стране, где у вас есть юрлицо, — Stripe. Схему БД менять не
придётся в обоих случаях.

**Перед Ф6 проверить:** что Stripe работает в стране регистрации
бизнеса.

## 3. Язык интерфейса — только английский

**Решение (владелец, приёмка Ф1).** Только английский, словарей и
локалей нет.

**Как устроено.** Интерфейс только на английском: `<html lang="en">`, тексты
написаны прямо в компонентах, словарей нет. Язык генерируемого контента
библиотека i18n не затрагивает: его задают промпт и профиль компании.

**Цена решения.**
- Остаёмся на одном языке — ничего делать не нужно.
- Добавляем языки позже — придётся вынести все строки интерфейса в
  словари и добавить локаль в маршрутизацию (`/ru/...`). Работа
  механическая, но затрагивает почти каждый компонент, и чем больше
  экранов, тем она дороже.

Если второй язык понадобится, это отдельная задача с ценой, описанной
выше.

## 4. AI — Claude через AI Provider Gateway

**Решение.** Бизнес-логика вызывает единый интерфейс `AIProvider`
(`lib/ai-provider/`), а не SDK провайдера напрямую. Реализован Claude
(`claude.ts`), модель по умолчанию — `claude-sonnet-5`
(`DEFAULT_AI_MODEL`). OpenAI, Gemini, Mistral и Grok — типизированные
заглушки. Модель зафиксирована в конфигурации: обновление SDK или
провайдера её не меняет.

**Почему.** Провайдеро-независимость — требование архитектуры (§6).
Смена модели — это переменная окружения, новый провайдер — это одна
реализация интерфейса.

**Цена смены.** Перейти на другую модель Claude — поменять env и
прогнать тесты провайдера. Подключить другого провайдера — дописать его
класс (ключи в `.env.example` уже зарезервированы). Выбор модели влияет
на себестоимость генерации: её измеряем в Ф4.

## 5. Рендеринг — динамический везде, без слоя кэша

**Решение.** Страницы рендерятся на сервере при каждом запросе (в
`next build` они помечены `ƒ`). Причина: layout'ы обеих групп маршрутов
читают сессию пользователя из cookies, чтобы показать навигацию.
С Ф7 динамические все, включая `/register`, `/register/check-email`,
`/reset-password` и 404: корневой layout читает nonce для CSP. Кэша данных (ISR, `revalidate`) нет. После
изменений Server Actions вызывают `revalidatePath` — поэтому у `/history`
и `/profile` нет `loading.tsx` (см. технические решения Фазы 5).

**Почему.** Почти каждая страница персональная: лимиты, история,
профиль. Кэширование было бы оптимизацией без замера.

**Следствия.**
- Для Ф7 это плюс: CSP с nonce и так требует динамического рендеринга,
  поэтому ничего не теряется.
- Скорость страниц зависит от запросов к Supabase — это меряем в Ф7.
- Главная страница тоже динамическая, потому что её layout читает
  сессию. Если в Ф8 для SEO понадобится статический лендинг, проверку
  сессии для неё придётся перенести на клиент. Сейчас это не нужно.

## 6. Монетизация: go / no-go — открыто

**Вопрос.** Переходить ли к Ф6 (оплата), или сначала доработать продукт.
Отвечает закрытая бета (`docs/beta.md`): 10–20 внешних пользователей,
две недели.

**Что записать сюда после беты:** цифры (регистрации, активация, медиана
времени до первого результата, вернулись ли люди, сколько человек
написали отзыв), три самых частых замечания, себестоимость генерации
против планируемой цены (README → Operations) — и решение с причиной.

**Решает владелец.**

## Технические решения Фазы 1 (Foundation)

- **Проверка окружения** (`lib/env.ts`) — zod-схема всех переменных.
  Выполняется при старте сервера, а не при сборке: CI собирает проект
  без секретов. Сборка на Vercel дополнительно требует
  `NEXT_PUBLIC_SUPABASE_*`, потому что эти значения вшиваются в
  браузерный код.
- **Sentry** — на сервере подключён полностью. В браузере SDK
  загружается только в момент ошибки (`lib/report-client-error.ts`): в
  общем бандле он добавлял 59 kB gzip к каждой странице. Сбор данных
  урезан до стека ошибки (`lib/sentry.ts`). Без DSN Sentry выключен.
- **Логи** (`lib/logger.ts`) — JSON-строки, `error` уходит в Sentry.
  Отдельную библиотеку логирования не добавляли: хватает `console`,
  который собирает Vercel.
- **Security-заголовки** — HSTS (пока без `includeSubDomains`/`preload`,
  они зависят от домена), `nosniff`, `Referrer-Policy`,
  `frame-ancestors 'none'`. Полная CSP — в Ф7.
- **Окружения** — Development (локальный Supabase CLI), Preview (Vercel +
  Supabase staging), Production (Vercel + Supabase prod). Миграции —
  через `supabase db push`, сначала на staging.
- **shadcn/ui не добавлен.** Роль дизайн-системы уже выполняет
  `components/ui/` на CSS-переменных (Stage 14). Замена библиотеки
  компонентов — визуальное решение, его принимает владелец продукта.

## Технические решения Фазы 5 (UX)

- **Next.js 15.5 и React 19** вместо Next.js 14. У 14.2.35 — 2 critical и
  8 high уязвимостей, исправления выходят только для 15.5.24+; ветка 15.5
  получает бэкпорты. Переход на 16 — отдельный шаг (Dependabot предложит).
- **Формы после ошибки не теряют введённое.** React 19 сбрасывает поля
  формы после action; email и текст возвращаются из action и становятся
  `defaultValue`, пароли — нет (очищаются, как и раньше).
- **Нет `loading.tsx` у `/history` и `/profile`.** В Next.js 15 страница,
  которую Server Action возвращает после `revalidatePath`, при
  `loading.tsx` вокруг неё иногда не отрисовывается (vercel/next.js#87529):
  звезда избранного не переключалась, «Saving…» не пропадало. Вернуть
  скелетоны можно, когда баг исправят.
- **Отзывы** — таблица `feedback` только для сервера (без прав у
  клиентов), 10 сообщений в час на человека, читаются SQL-запросом.
- **Бэкапы** — ежедневные бэкапы Supabase Pro плюс `supabase/backup.sh`:
  обычный dump/restore из документации Supabase терял триггер регистрации
  и права клиентов (`docs/backup-restore.md`).
- **Доступность проверяет CI** — axe (WCAG 2.1 AA, critical/serious) и
  отсутствие горизонтальной прокрутки на 360px, в светлой и тёмной теме.
- **Ошибки считаем на генерацию, а не на сессию.** Sentry собирает только
  ошибки и ничего не знает о людях (Ф1), поэтому критерий «ошибок меньше
  1% сессий» меряется как события Sentry ÷ генерации (`docs/beta.md`).

## Технические решения Фазы 6 (Monetization)

- **Тариф — только из подписки.** План пользователя — лучший из его
  подписок в статусе `active` или `trialing`; `users.plan_id` удалён
  (миграция 0024). `past_due`, `unpaid` и `canceled` дают Free.
- **Пишет только сервер, данными Stripe.** Вебхук проверяет подпись,
  пропускает уже обработанные события (`stripe_events`) и перечитывает
  подписку из Stripe вместо того, чтобы верить копии в событии. Ночная
  сверка делает то же самое для всех подписок.
- **Какой тариф даёт цена** — по её lookup key в Stripe (`pro_monthly`),
  а не по id в переменных окружения: одинаково в test и live.
- **Trial 14 дней**, один на человека (нет trial после любой прошлой
  подписки), карта берётся сразу. Длительность — `TRIAL_DAYS` в
  `lib/billing/stripe.ts`; владелец может поменять.
- **Enterprise** остаётся по договорённости: «Contact us», цена с ключом
  `enterprise_…` создаётся вручную под клиента.
- **Удаление аккаунта** сначала удаляет клиента в Stripe (подписка
  заканчивается сразу), иначе Stripe продолжал бы списывать деньги.
- **Без ключей** оплата выключена, интерфейс как раньше. E2E гоняет все
  сценарии через локальную заглушку Stripe (`e2e/mock-stripe.mjs`).
- **Маржа** (`docs/billing.md`): Pro выгоден, пока пользователь не тратит
  все 500 генераций на длинные тексты; в худшем случае — минус около
  $17 в месяц. Решение (лимит или цена) — за владельцем после беты.

## Технические решения Фазы 7 (Production)

- **CSP с nonce, а не с хэшами.** Next.js встраивает свои скрипты с
  данными каждой страницы, хэши их не покрывают. Все страницы и так
  динамические (§5). Политика строится в `lib/csp.ts`, ставится в
  `middleware.ts`; `'strict-dynamic'` пропускает то, что загружают
  доверенные скрипты (чанки, Sentry по требованию).
- **Стили — с `'unsafe-inline'`.** React рендерит атрибуты `style`
  (полоска расхода в UsageCard); код через CSS не запускается.
- **Report-Only — переключатель, а не другая политика.**
  `CSP_REPORT_ONLY=true` отправляет ту же политику в режиме отчётов.
  По умолчанию политика включена: E2E проходит под ней без нарушений.
  Отчёты приходят в `/api/csp-report` → лог и Sentry (warning).

## Технические решения Фазы 8 (Launch)

- **Визиты без cookies.** Первый шаг воронки — событие `site_visited`
  с сервера (middleware). Посетитель — псевдонимный ID: HMAC от даты, IP
  и браузера на серверном ключе, меняется каждый день; на устройстве
  ничего не хранится, поэтому баннер согласия не нужен (как решено в
  Ф4 для PostHog). Регистрация связывает ID этого дня с аккаунтом.
  Навигацию определяет `sec-fetch-mode`: service worker пересылает
  переходы с `sec-fetch-dest: empty`.
- **Оплата в воронке** — из вебхука Stripe: `subscription_started`
  (Checkout завершён) и `payment_succeeded` (счёт, по которому списаны
  деньги).
- **Кто управляет сервисом** (юрлицо, страна, почтовый провайдер) и
  адрес поддержки — переменные окружения, обязательные в production: с
  заглушками прод не стартует; в остальных окружениях страницы
  помечены «Draft».
- **Цифры в FAQ и на лендинге** берутся оттуда же, откуда их берёт
  приложение (тарифы из БД, длина trial, гостевой лимит), а не пишутся
  руками.
- **Индексируется только production:** `robots.txt` для остальных
  окружений запрещает всё; sitemap строится на каждый запрос (список
  инструментов — из БД).
