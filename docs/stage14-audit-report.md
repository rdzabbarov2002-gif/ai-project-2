### 3–5. Расширение vs новая сущность, YAGNI, SRP

Ни один существующий файл не годился для расширения под "список из многих записей с join на tools/templates" — все существующие резолверы рассчитаны на одну строку по `slug`. Новый компонент (`HistoryItem`) и две новые страницы — обоснованы по прецеденту `ToolCard`/`TemplateCard` (одна ответственность каждый: отрисовать одну запись / прочитать и показать список / прочитать и показать одну запись). Ни `HistoryService`, ни `HistoryRepository`, ни `QueryBuilder` не создавались — прямые Supabase-запросы, тот же путь, что везде в `(auth)/`.

## 3. Архитектурные решения

**Join `tools(name)`/`templates(name)` в одном запросе, а не вызов `resolveTool()`/`resolveTemplate()` по каждой строке.**
Эти функции принимают `slug`, а не `tool_id`/`template_id`, которые реально хранятся в `generations` — вызвать их напрямую было бы нельзя без дополнительного маппинга id→slug, а вызов по одному на строку означал бы N+1 запросов там, где один embedded-select отвечает за один round-trip. Та же логика, что уже обосновывала `lib/templates/catalog.ts` в Stage 10.

**Пагинация — offset-based через `?page=`, без отдельного `COUNT(*)`.**
Первая пагинация в проекте — расширять было нечего. Реализована минимально: запрашивается `PAGE_SIZE + 1` строк, наличие "лишней" определяет, показывать ли "Next" — без дополнительного запроса на подсчёт общего числа записей. Тот же паттерн "необязательный `searchParams`-параметр на серверной странице", что уже использован для `?template=` (Stage 10).

**"Открытие" записи — отдельная read-only страница `/history/{id}`, не inline expand/collapse.**
Рассмотрено явно. Inline-разворачивание потребовало бы сделать список (или каждую строку) клиентским компонентом с состоянием; отдельная серверная страница — ноль клиентского JS, тот же паттерн "список + деталь", что уже используют `/tools` → `/tools/{slug}`. Простое решение оказалось одновременно и более простым технически, и более последовательным архитектурно.

**У `/history/[id]` нет собственных `loading.tsx`/`error.tsx`.**
Проверено по прямому прецеденту: `/tools/[slug]` (Stage 6/8/10) никогда их не получал — только страницы-списки (`/tools`, `/templates`, `/history`) имеют loading/error по конвенции Next.js. Сохранена та же граница, а не изобретена новая.

**Кнопка "Copy" на детальной странице сознательно не добавлена.**
`ToolRunner`'s панель результата такую кнопку имеет, и добавление её сюда для паритета было бы логичным улучшением — но потребовало бы Client Component ради функциональности, явно не запрошенной текстом Stage 14. Текст результата доступен для выделения и копирования штатными средствами браузера без единой строки клиентского кода.

**"Статус" не отображается нигде.**
В `generations` нет колонки статуса — задание явно формулирует это поле как условное ("если уже хранится"). Условие не выполнено, поле не отрисовывается.

**Favorites не затронуты.**
RLS `UPDATE`-политика уже это поддерживает (заложено ещё в Stage 3 именно под историю), но задание Stage 14 нигде не просит переключатель избранного — интерфейс для него не создан, хотя инфраструктура для этого уже существует и ничего не мешает добавить его позже без единой правки RLS.

## 5. Что невозможно проверить

- **Реальное чтение `generations` с join'ом `tools`/`templates` против живой БД** — сети нет, как во всех предыдущих стадиях.
- **Реальное поведение `.range(offset, offset + PAGE_SIZE)`** — синтаксис соответствует документированному API `@supabase/supabase-js` (inclusive range), но не выполнялся вживую именно с этой комбинацией смещения и лимита.
- **Реальный сценарий "гость сгенерировал → зарегистрировался → merge перенёс генерации → они появились в истории"** — каждое звено проверено по отдельности статически в своих стадиях (5, 8, 11), полная цепочка целиком не запускалась.
- **Визуальный вид списка/детали в браузере** — разметка использует только существующие токены и компоненты, но не рендерилась.

## 7. Потенциальные риски первой сборки

Только реальные:

1. **Нетипизированный embed-запрос `tools(name)`/`templates(name)`** — та же, уже трижды документированная (Stage 5, 8, 10) оговорка: `database.types.ts` написан вручную, не несёт `Relationships`-метаданных, поэтому форма вложенного результата (объект vs массив) защищена явным приведением типов, но не проверена вживую именно для этой комбинации таблиц.
2. **`.range()` с `offset` больше реального числа строк** (глубокая страница за пределами данных) — Supabase в этом случае должен вернуть пустой массив, не ошибку; код (`rows.length > PAGE_SIZE` → `false`, `generations` → `[]` → Empty State) обрабатывает это корректно по логике, но такой конкретный граничный случай не проверялся вживую.

## 8. Компромиссные решения

Одно, явно не техдолг: **пагинация без общего счётчика записей** ("страница 3 из 12" невозможна, только Next/Previous). Это не временное решение, которое Stage 15 или что-либо ещё обязано заменить — для списка, отображаемого сегментами по 10, знание точного общего числа не несёт функциональной пользы, а его получение стоило бы дополнительного `COUNT(*)`-запроса на каждую загрузку страницы. Если в будущем понадобится другой вид пагинации (например, для админ-панели), это отдельная, отдельно обоснованная задача — не доработка данного минимального решения.

## 10. Почему Stage 15 можно начинать без переписывания Stage 14

Stage 15 (по исходному плану — финальный аудит и релиз) не требует от Stage 14 никакой конкретной внутренней структуры для повторного использования: История — самодостаточная пара "список + read-only деталь" поверх уже существующей таблицы, ничего не пишет, ни от чего не зависит из будущих стадий. Единственное, что Stage 15 могло бы захотеть сделать с этой стадией — сквозная проверка (реальный e2e-прогон списка/пагинации/детали против живой БД), а не переработка кода: логика уже статически проверена и построена на тех же, уже пять раз подтверждённых паттернах (RLS-scoped прямой запрос, `searchParams`-конфигурация, list+detail через маршрутизацию), что и весь `(auth)/`-раздел проекта.
