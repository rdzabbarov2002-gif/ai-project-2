## 3. Найденные проблемы и что сделано

### Безопасность

| # | Проблема | Насколько серьёзно | Исправление |
|---|---|---|---|
| 1 | **Бесконечные бесплатные генерации.** Гость — это любой, кто прислал новый токен сессии; токен создаёт браузер. Скрипт с новым токеном на каждый запрос получал 3 бесплатные генерации снова и снова — прямые расходы на OpenAI без ограничения. Поминутный лимит тоже считался на токен и обходился так же | Высокая (деньги) | Лимит генераций без аккаунта на IP-адрес: 20 в сутки (`GUEST_GENERATIONS_PER_IP_PER_DAY`). Проверяется **до** создания гостевой сессии. Сверх лимита гостю предлагается бесплатная регистрация — тот же экран, что и после 3 генераций. IPv6 считается по сети /64 (один абонент получает всю /64 и иначе мог бы менять адрес на каждом запросе) |
| 2 | **Поминутный лимит обходился одновременными запросами.** Он считал сохранённые генерации, а строка появляется только после ответа ИИ (10–50 с). Десять запросов, отправленных разом, проходили все | Средняя–высокая | Лимит считает запросы в момент начала: таблица `rate_limit_events` и функция `take_rate_limit` (миграция 0027) с блокировкой на субъект — из 12 одновременных запросов при лимите 3 проходят ровно 3 (проверено на PostgreSQL) |
| 3 | **Прямая запись генераций через публичный API.** Вошедший пользователь мог через REST-API Supabase со своим токеном вставлять в `generations` сколько угодно строк любого размера в обход всех лимитов | Средняя–высокая (заполнение базы) | Право INSERT для клиентов отозвано (миграция 0026); генерации сохраняет только сервер |
| 4 | **Профили компании без ограничений в базе.** Лимиты длины были только в форме; через API можно было писать мегабайты и тысячи профилей | Средняя | Ограничения длины в самой базе (те же, что в форме) и не больше 20 профилей на пользователя (миграция 0026; существующие строки не перепроверяются — `not valid`) |
| 5 | **Заполнение базы без регистрации.** `/api/session/draft` без входа создаёт строку на каждый новый токен — скрипт мог заполнить бесплатные 500 МБ Supabase за часы | Высокая (отказ в обслуживании) | 30 сохранений черновика в час с одного IP |
| 6 | **«Зависание» сервера при автозаполнении по сайту.** Разбор HTML регулярными выражениями шёл за квадратичное время: страница из символов `<` размером 40 КБ — 2,2 с (замер), на допустимых 1,5 МБ — по расчёту около 50 минут процессора. Злоумышленнику достаточно указать свой сайт | Высокая (отказ в обслуживании) | Разбор переписан на линейный: любая страница до 1,5 МБ — меньше 0,11 с. Результат для обычных страниц тот же (старые тесты проходят), добавлены тесты на враждебные страницы |
| 7 | **Автозаполнение без лимита.** Каждый вызов — запрос к сайту и вызов ИИ, которые не учитывает ни один тариф | Средняя (деньги) | 10 автозаполнений в час на пользователя |
| 8 | **Исчерпание квоты Sentry.** `/api/csp-report` принимает отчёты от кого угодно, каждый уходит в Sentry; когда квота кончается, Sentry перестаёт принимать и настоящие ошибки | Низкая–средняя | 20 отчётов в час с одного IP; мусорные запросы базу не трогают |
| 9 | **Уязвимые зависимости.** zod < 4.6.6 — исчерпание памяти при проверке огромных массивов (высокая; zod проверяет тела запросов в продакшене); Next.js — критические уязвимости, закрытые в 15.5.28; vitest/tinypool — критическая и средняя (только инструменты тестов) | Высокая | zod 4.6.7 (код адаптирован), Next.js 15.5.28, vitest 5.0.5, sharp и source-map-js через `npm audit fix`. `npm audit`: 0 |
| 10 | **Адрес сайта в письмах из заголовка запроса.** Без `NEXT_PUBLIC_SITE_URL` ссылки подтверждения и сброса пароля строятся из заголовка Host. На Vercel его подделать нельзя, и Supabase сверяет адрес со списком разрешённых, но это две внешние защиты вместо одной своей | Низкая | В продакшене `NEXT_PUBLIC_SITE_URL` обязателен (сервер не стартует без него), как и `CRON_SECRET` (иначе не работают ночные задачи, включая удаление данных) |
| 11 | Токен в `/api/session/merge` проверялся только на «строку» | Низкая | Те же границы длины (10–200), что во всех остальных местах |

### Конфиденциальность

| Проблема | Исправление |
|---|---|
| Политика обещала, что гостевые сессии «истекают через 30 дней», но ничто их не удаляло: сессии, черновики профиля и гостевые генерации хранились вечно | Ночная задача `/api/cron/purge-expired` (`vercel.json`) удаляет гостевые сессии через 30 дней после последнего использования вместе с их генерациями, и записи лимитов старше суток |
| После регистрации гостевая сессия (токен и черновик профиля) оставалась на сервере, хотя всё уже перенесено в аккаунт | Сессия удаляется сразу после переноса |
| Новые записи лимитов — это данные об активности | IP не хранится: только ключевой хэш, который меняется каждый день и удаляется в течение двух суток. Политика конфиденциальности дополнена (раздел «Abuse protection» и сроки хранения) |

Проверено и в порядке: в логах нет email и текстов пользователей (logger
отбрасывает `details` ошибок PostgREST), PostHog получает только
идентификаторы, CSP-отчёты обрезают query string, сервис-воркер не кэширует
страницы и API.

### Производительность и масштабируемость

| Проблема | Исправление |
|---|---|
| Middleware на **каждый** запрос (страницы, API, переходы) ходил в Supabase Auth (`getUser`) — лишний сетевой запрос (десятки миллисекунд) и нагрузка на Auth, растущая с числом пользователей | `getClaims()`: при асимметричных ключах подписи проверка подписи токена локально (ключи загружаются раз и кэшируются); при старом общем секрете — как раньше. Защищённые страницы и все маршруты по-прежнему проверяют пользователя через Auth сами |
| Аналитика задерживала ответы (генерации, регистрации) на время запроса к PostHog — до 2 с при его медленной работе | События уходят после ответа (`after()` из Next.js) |
| Гостевая сессия: чтение + обновление или вставка — два запроса и гонка при первом обращении | Один `upsert` |
| Контексты Toast и GuestSession создавали новый объект на каждую перерисовку → лишние перерисовки потребителей | `useMemo` |

## 4. Ложные срабатывания — проверил, проблемы нет

| Подозрение | Почему не проблема |
|---|---|
| `dangerouslySetInnerHTML` в `app/layout.tsx` | Два статических скрипта (тема, сервис-воркер) без пользовательских данных, с nonce CSP |
| SSRF через автозаполнение по URL | Защита полная: проверка всех IP из DNS, запрет частных диапазонов и метаданных облака, подключение к уже проверенному адресу, повторная проверка каждого редиректа, лимит 1,5 МБ |
| Подмена IP через `X-Forwarded-For` | На Vercel заголовок выставляет платформа, внешнее значение не проходит |
| Секреты в браузере | В `NEXT_PUBLIC_*` только публичные значения; anon-ключ Supabase публичен по задумке, данные защищает RLS (тесты RLS это проверяют) |
| Open redirect после входа | `lib/safe-redirect.ts` пропускает только внутренние пути, покрыт тестами |
| Сервис-воркер кэширует чужие данные | Кэширует только статические файлы сборки и иконки; страницы и API — всегда из сети |
| Утечки подписок и таймеров | Подписка на события Auth и слушатель темы снимаются при размонтировании |
| «Неиспользуемые экспорты» из сканера | Это типы и константы, которые используются внутри своих файлов — не мёртвый код |
| Cookie сессии без `HttpOnly` | Так устроен `@supabase/ssr`; защита — CSP и экранирование React (решение зафиксировано в `docs/security-checklist.md`) |

## 5. Что оставлено без изменений и почему

| Что | Почему |
|---|---|
| Клиент Supabase (~79 КБ) загружается на каждой странице из-за `AuthSyncListener` | Чтобы убрать, нужно перестроить перенос гостевых данных при регистрации, а e2e-тестов на этот перенос нет. Риск сломать перенос данных выше пользы |
| ESLint 8 (поддержка закончилась) и `next lint` (объявлен устаревшим) | Уязвимостей нет; переход на ESLint 9 и flat config — смена инструментов, а не исправление. Сделать до перехода на Next.js 16 |
| Заглушки провайдеров Gemini, Mistral, Grok | Часть архитектуры шлюза (типизированные заглушки, документированы) |
| `max_saved_results` и `max_company_profiles` из тарифов не применяются | Это продуктовое решение (что показывать при превышении), а не ошибка. Предохранитель на 20 профилей в базе — не тарифный лимит |
| Месячный лимит проверяется до генерации, а засчитывается после — параллельные запросы могут превысить его на несколько штук | Теперь превышение ограничено поминутным лимитом (6). Полностью атомарная проверка потребовала бы перестройки пайплайна |
| Markdown не форматируется Prettier | Отчёты и документы написаны вручную с выровненными таблицами; переформатирование дало бы тысячи строк изменений без пользы |
| Сообщения об ошибках валидации стали формулировками zod 4 | Видны только при некорректном запросе к API в обход интерфейса; для русского интерфейса используется свой перевод |
| `actions/checkout@v4` (предупреждение GitHub про Node 20) | Работает: GitHub сам запускает его на Node 24. Обновление до v5 — отдельная задача без пользы для продукта сейчас |

## 6. Ограничения и риски, которые остаются

1. **Лимиты по IP останавливают одного человека, но не того, у кого много адресов** (ботнеты, прокси). Следующий шаг — капча на гостевую
   генерацию; это новая функция, поэтому не добавлялась.
2. **Вход и регистрация вызывают Supabase Auth с сервера**, поэтому лимиты Supabase «на IP» относятся к адресам Vercel, а не к посетителю:
   защита от перебора паролей по IP посетителя слабее, а при большом трафике общий лимит может мешать. Проверить лимиты в Supabase →
   Authentication → Rate Limits и включить капчу Supabase Auth.
3. **Квоту Sentry можно исчерпать с многих IP** — поставить лимит на ключ в настройках проекта Sentry.
4. **Если база недоступна, лимиты пропускают запросы** (сделано сознательно: иначе сбой базы остановил бы все генерации; месячные лимиты
   при этом всё равно работают).
5. **Порядок развёртывания в продакшене:** сначала код, потом миграции 0026 и 0027. Новый код работает и без них (лимиты пропускают всё,
   пока нет 0027), а старый код после 0026 не сможет сохранять генерации вошедших пользователей.
6. **Тарифы платформ:** бесплатный Supabase приостанавливает проект после недели без активности (это и случилось со staging) и ограничен
   500 МБ; бесплатный Vercel (Hobby) по правилам — только для некоммерческого использования. Для платного сервиса нужны платные тарифы.
7. **Проверено не всё локально:** Docker не смог скачать образы Supabase (ограничение реестра в этой среде), поэтому e2e-тесты здесь не
   запускались — их запускает CI. Миграции и тесты базы проверены на PostgreSQL 16 с заменой схемы `auth` и ролей Supabase; типы для
   новой таблицы написаны вручную в формате генератора — CI сверяет их с настоящим генератором.
