## 3. Архитектурные решения и почему

**`lib/templates/` — новый модуль, а не расширение `lib/generation/catalog.ts` или `lib/tools/`.**
Прошёл чек-лист задания перед написанием кода: существует ли уже механизм листинга нескольких шаблонов сразу — нет (`resolveTemplate`/`resolveDefaultTemplate` — только резолвинг одной строки, для пайплайна и страницы инструмента). Можно ли расширить `lib/tools/` — нет, это другая сущность с другой формой данных. Итог: новый модуль оправдан тем же способом, каким Stage 7 обосновал появление `lib/tools/` рядом с `lib/generation/catalog.ts` — не вторая версия существующего, а параллельный, самостоятельный слой чтения для другого потребителя.

**Фильтр `.eq("tools.is_active", true)` в `listTemplates()` — обязательная находка, исправленная сразу.**
RLS-политика `templates` (`using (true)`, миграция 0006) не каскадирует `is_active` родительского инструмента — она в принципе не знает о таблице `tools`. Это не проявлялось раньше: `resolveTemplate`/`resolveDefaultTemplate` вызываются только после того, как `resolveTool()` уже подтвердил активность инструмента (пайплайн, страница инструмента) — обходной путь просто не был достижим. `listTemplates()` — первая функция, которая читает `templates` *без* предварительного прохода через `resolveTool()`, и потому первая, где этот пробел стал реально достижимым: без фильтра карточка могла бы вести на инструмент, показывающий "This tool isn't available". Ответ на обязательный вопрос "нужно ли исправлять именно для Stage 10" — да: без этого библиотека шаблонов был бы сломана по построению. Исправлено на уровне запроса (`tools!inner(...)` + `.eq("tools.is_active", true)`) внутри нового файла, а не правкой RLS-политики или какого-либо существующего файла — нулевое изменение уже существующего кода.

**`SearchBar` получил два опциональных пропа вместо создания второго компонента.**
Рассмотрел оба варианта. Дублирование ради двух строк текста нарушило бы DRY без причины (вся логика идентична, отличается только строка). Изменение — строго аддитивное (новые параметры не обязательны, есть дефолты, воспроизводящие точное прежнее поведение), вызов в `ToolGallery.tsx` не тронут и не нуждался в правке — проверено явно (см. §9). `CategoryFilter` изменений не потребовал вообще: его единственный видимый текст ("All categories", `aria-label="Filter by category"`) уже был нейтральным.

**`TemplateCard`/`TemplateGrid`/`EmptyState`/`LoadingState`/`ErrorState` — независимые реализации, не переиспользование одноимённых компонентов из `components/tools/gallery/`.**
В отличие от `SearchBar`/`CategoryFilter`, эти компоненты либо рендерят другую форму данных (`ToolCard` использует `icon`/`description`, которых нет у шаблонов), либо содержат захардкоженный, специфичный текст ("Loading tools…", `"no-tools" | "no-results"` как буквальный union-тип). Расширение существующих компонентов означало бы правку уже отгруженного, проверенного кода Stage 7 без объективной необходимости — прямо запрещено правилом 6 этой стадии. Каждый новый компонент — несколько строк, самостоятельная копия паттерна, не общего кода.

**`lib/templates/query.ts` не делит общую абстракцию с `lib/tools/query.ts` — сознательное решение, не недосмотр.**
Обе функции фильтруют/сортируют список по имени, категории и опциональному поиску — структурно похожи. Разделяемая абстракция потребовала бы либо переписать `lib/tools/query.ts` (Stage 7, уже сдан, без необходимости для Stage 10), либо оставить два разных подхода к одинаковой задаче (ещё хуже). Поля поиска у двух сущностей и так уже отличаются (name+description против name+category — у шаблонов нет `description`), и это разойдётся ещё больше, если, например, Stage 13 добавит фильтр по `is_premium` только для шаблонов. Разделяю паттерн, не код — та же логика, что обосновывала появление `lib/tools/` рядом с `lib/generation/catalog.ts` в Stage 7.

**`?template=` на странице инструмента: переиспользование уже существующей функции, не новая логика резолвинга.**
`resolveTemplate(supabase, slug, toolId)` существует с Stage 5, использовалась ровно в одном месте (`/api/generate`) — теперь используется и здесь, без единой правки самой функции. Невалидный/устаревший `?template=` (опечатка, инструмент не совпадает, шаблон удалён) не подставляется на дефолтный шаблон незаметно для пользователя — резолвится в `null`, и `ToolRunner` откатывается к уже существующему (с Stage 5) обобщённому промпту без шаблона. Явный выбор шаблона либо срабатывает, либо явно не срабатывает — никогда не подменяется на что-то другое молча.

**Ни одной новой колонки в БД.**
Рассмотрел и отклонил: `templates.description` (по аналогии с тем, как Stage 7 добавил `tools.description`) — не запрошено в задании Stage 10 (в отличие от Stage 7, где список полей карточки инструмента был явно перечислен), а имени+категории+инструмента достаточно для карточки. Добавление колонки без прямого требования было бы ровно тем "на будущее", которое запрещено правилом этой стадии.

## 10. Почему Stage 11 можно начинать без переписывания Stage 10

Stage 11 (по исходному плану — "Регистрация + merge гостя") не имеет прямой функциональной связи с Templates Library. Ничего в этой стадии не создаёт зависимости, которые Stage 11 должен был бы учитывать или обходить: `lib/templates/`, `components/templates/` и правка `?template=` на странице инструмента — самодостаточные, не читают и не пишут ничего, связанного с сессией гостя или её переносом в аккаунт при регистрации (`generations`, `guest_sessions` эта стадия не трогала вообще). Если Stage 11 когда-либо коснётся страницы `/tools/{slug}`, единственное, что ему нужно будет учитывать — что `searchParams.template` теперь читается там наравне с `params.slug`, то есть не больше, чем любое другое уже существующее поведение этой страницы.
