## 3. Почему выбраны такие решения

**Двухуровневая защита `(auth)`-маршрутов (middleware + layout).**
Middleware защищает на edge и не даёт дойти до рендера вовсе — это быстро и покрывает основной случай. Но middleware можно обойти в редких случаях (например, прямой вызов Server Action) или сломать неосторожной правкой `matcher` в будущих стадиях. `app/(auth)/layout.tsx` — второй, независимый чек на сервере, который гарантирует: если он не сработал — значит баг в самом layout, а не забытая строчка в middleware. Небольшая избыточность ради того, чтобы защищённый контент физически не мог отрендериться для неавторизованного запроса.

**`getUser()`, а не `getSession()`, в middleware и layout.**
`getSession()` в SSR-контексте не валидирует токен заново — доверяет тому, что лежит в cookie. `getUser()` делает реальный запрос к Supabase и подтверждает, что токен всё ещё действителен. Это стандартная рекомендация `@supabase/ssr` для любого кода, принимающего решение о маршрутизации, и разница напрямую влияет на безопасность.

**Merge-эндпоинт возвращает `200 {status: "deferred"}`, а не ошибку.**
Технически "мы ничего не перенесли" — но запрос корректен и завершится успехом, как только появится хранилище (Stage 3) и логика переноса (Stage 11). Ответ с кодом ошибки заставил бы клиент трактовать это как сбой и, например, ретраить или показывать пользователю сообщение об ошибке — то есть создавать ложное впечатление проблемы там, где её нет. `AuthSyncListener` явно закодирован под оба состояния (`merged` / `deferred`) уже сейчас, чтобы в Stage 11 понадобилось поменять только сам эндпоинт, а не клиентский код.

**Гостевой токен не удаляется до реального подтверждения merge.**
Если бы `AuthSyncListener` чистил localStorage сразу после регистрации, а эндпоинт ничего на самом деле не сохранял (пока нет таблиц) — черновик профиля и история гостя были бы потеряны безвозвратно. Токен остаётся в localStorage до тех пор, пока сервер не подтвердит `status: "merged"`, что произойдёт только в Stage 11. Это прямое исполнение принципа "переход без потери данных" из утверждённой архитектуры, физически проверяемое уже на этой стадии.

**`searchParams` как проп, а не `useSearchParams()`, на странице логина.**
Разбор ниже, в разделе про риски первой сборки — коротко: тот же результат, но без обязательного `<Suspense>`, который иначе требуется Next.js.

**`server-only` вместо просто комментария "не импортировать на клиенте".**
`lib/supabase/auth.ts` использует `redirect()` и предполагается только для серверного кода. Пакет `server-only` превращает случайный импорт этого файла в клиентский компонент в ошибку сборки, а не в рантайм-баг, который проявится только у реального пользователя.

## 4. Обнаруженные проблемы

| Проблема | Статус |
|---|---|
| `useSearchParams()` в клиентском компоненте страницы `/login` без `<Suspense>` — известная причина ошибки `next build`: *"useSearchParams() should be wrapped in a suspense boundary"* | **Исправлено** — заменено на стандартный проп `searchParams`, который Next.js передаёt в `page.tsx` без дополнительных условий |
| Риск случайного использования `SUPABASE_SERVICE_ROLE_KEY` на клиенте при развитии auth-логики | **Исправлено превентивно** — такой клиент по-прежнему нигде не создан; `lib/supabase/auth.ts` защищён `server-only` |
| Merge мог быть реализован "оптимистично" (чистить гостевой токен сразу после ответа 200) — привело бы к потере данных гостя при реальном подключении Stage 11, если бы логика клиента не была продумана заранее | **Исправлено в дизайне** — токен чистится только по `status: "merged"` |
| `guest_session_token` в `/api/session/merge` мог не валидироваться вовсе (просто прокидываться дальше) | **Исправлено** — явная проверка наличия и типа поля, `400` при некорректном теле |

Критических ошибок, блокирующих Stage 3, не обнаружено.

## 5. Что нельзя проверить в текущей среде

- **Установка зависимостей.** `npm install` физически невозможен — в контейнере нет доступа к сети (подтверждено: `npm ping` вернул `403 Forbidden`). Пакет `server-only`, добавленный в этой стадии, не был реально установлен и слинкован — только прописан в `package.json`.
- **Реальный запуск `next dev`/`next build`.** Соответственно, полноценная проверка типов (`tsc` с реальными `@types/react`, `@types/node`, типами Next.js и Supabase) не выполнялась — без установленных зависимостей `tsc` выдаёт тысячи нерелевантных "module not found", а не реальные ошибки в моём коде.
- **Поведение Supabase Auth end-to-end** (реальная отправка email-подтверждения, реальный `exchangeCodeForSession`, реальные cookie в браузере) — не проверялось и не может быть проверено без живого проекта Supabase, который появится в Stage 3.

## Что было сделано вместо этого, чтобы снизить риск

- Синтаксическая проверка каждого нового `.ts`-файла напрямую через `node --experimental-strip-types --check` — реальный парсер, не эвристика. Все файлы прошли без ошибок.
- Для `.tsx`-файлов (JSX не парсится напрямую `node`) — ручная проверка баланса `{}`/`()` по каждому файлу плюс построчное ревью.
- Сверка **каждого** импорта через алиас `@/...` и каждого относительного импорта (`./actions`) с реально существующими файлами и реально экспортируемыми из них именами — не "похоже на правду", а построчный grep-аудит экспортов против использований (раздел был выполнен именно как проверка, а не как предположение).
- Проверка `package.json` на валидность JSON после правки.
- Явный разбор конкретного класса ошибок сборки (`useSearchParams` без `Suspense`) — найден и устранён до того, как стал бы сюрпризом при первой сборке в Replit/bolt.new.

## 6. Потенциальные ошибки первой сборки — на что обратить внимание

1. **`server-only`** — новая зависимость. Она обязана попасть в `npm install` при первом импорте в Replit/bolt.new; если импорт делается не из `package.json` (например, ручным копированием без переустановки), сборка упадёт на `Cannot find module 'server-only'`. Рекомендация: после импорта сразу выполнить `npm install`, не полагаться на кэш.
2. **Email confirmation в Supabase.** По умолчанию в новом Supabase-проекте подтверждение email включено — `signUp` не создаст сессию сразу, пользователя перебросит на `/register/check-email`. Это ожидаемое поведение (обработано веткой `data.session`), но если вы хотите более быстрый цикл тестирования на Stage 2-3, эту настройку можно временно отключить в Supabase Dashboard → Authentication → Providers → Email.
3. **`NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` пока не заполнены.** Любая страница, обращающаяся к Supabase (`/login`, `/register`, middleware), при пустых переменных окружения получит рантайм-ошибку "supabaseUrl is required" — это ожидаемо до Stage 3, когда проект Supabase будет создан, но стоит завести его пораньше, чтобы проверить сам Stage 2 живьём.
