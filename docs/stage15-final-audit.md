# Stage 15 — Финальный инженерный аудит

## AI Marketing Workspace — завершение проектирования MVP

Это не аудит одной стадии — это сплошная проверка всего проекта, Stage 1–14, заново и целиком, а не по памяти о прошлых частичных аудитах. Там, где прошлые аудиты что-то упустили, это зафиксировано явно (см. §1.9).

## 1. Полный аудит проекта

### 1.1 Архитектура и структура директорий

```
app/
  (guest)/          — публичные маршруты: /, /tools, /tools/[slug], /templates
  (auth)/            — защищённые middleware: /dashboard, /profile, /history, /history/[id], /settings/billing
  api/generate/      — Core Generate Pipeline (POST)
  api/session/merge/ — Guest→User merge (POST)
  auth/callback/     — Supabase email confirmation
  login/, register/  — публичные auth-формы
components/
  ui/                — 6 примитивов (Button, Card, Input, Textarea, Select, Checkbox)
  auth/, providers/  — Guest Session + Auth Sync
  tools/, tools/fields/, tools/gallery/  — ToolRunner + Tools Gallery
  templates/         — Templates Library
  profile/, usage/, history/  — по одному компоненту/набору на фичу
lib/
  supabase/          — 4 клиента (client/server/admin/middleware), единственная точка создания клиентов
  generation/         — Core Generate Pipeline (10 файлов)
  ai-provider/        — AI Provider Gateway (Claude реализован, 4 заглушки)
  tools/, templates/  — слои листинга для галерей (независимы от generation/)
  tool-config/         — формат config_schema (zod)
  guest-session/, limits/  — Guest Session, usage-лимиты
supabase/
  migrations/ (0001–0015)  — последовательны, без пропусков и дублей
  schema.sql, seed.sql      — актуальные конкатенации (сверено программно, см. 1.2)
```

Структура ровно соответствует тому, что документировали все 14 предыдущих аудитов — расхождений между "что должно быть" и "что реально есть на диске" не найдено.

**Итого файлов проекта: 146** (без `node_modules`).

### 1.2 Импорты — проверено программно, не выборочно

- **Все `@/...`-импорты** (абсолютные, через alias) по всем 146 файлам — резолвятся. 0 пропусков.
- **Все относительные импорты** (`./`, `../`) по всем файлам — резолвятся (с нормализацией путей через `os.path.normpath`). 0 пропусков.
- **Циклические зависимости** — построен полный граф импортов (107 исходных файлов, 206 рёбер) с DFS-поиском циклов. **Циклов не найдено.**
- **`schema.sql`** — построчно сверен с конкатенацией всех структурных миграций (0001–0009, 0011, 0012) — совпадает полностью (единственное расхождение в первом прогоне оказалось смещением на одну строку в моём же скрипте сравнения, не реальным расхождением содержимого — перепроверено).
- **`seed.sql`** — подтверждено содержит контент всех четырёх миграций данных (0010, 0013, 0014, 0015) — по характерным маркерам каждой.

### 1.3 Зависимости (`package.json`)

9 пакетов в `dependencies`, все явно используются (проверено по каждому): `next`/`react`/`react-dom` (фреймворк), `@anthropic-ai/sdk` (Stage 4, единственный реализованный провайдер), `@supabase/supabase-js` (admin-клиент), `@supabase/ssr` (browser/server/middleware-клиенты), `clsx` (UI-примитивы), `server-only` (граница клиент/сервер), `zod` (единственная система валидации). Библиотек-дублей (второй HTTP-клиент, вторая ORM, вторая валидация) не найдено.

### 1.4 SRP / DRY / KISS / YAGNI

Ни одного нарушения SRP не найдено — каждый новый файл каждой стадии обосновывался ровно одной ответственностью (зафиксировано в 14 предыдущих аудитах, перепроверено выборочно в этом).

DRY: два осознанных, зафиксированных компромисса, не нарушения:
- `lib/tools/query.ts` vs `lib/templates/query.ts` — структурно похожи, сознательно не объединены (Stage 10, подтверждено вновь в Stage 13 как прецедент).
- 6 небольших файлов `LoadingState`/`ErrorState`/`EmptyState` (`components/tools/gallery/`, `components/templates/`) + 6 файлов с инлайн-текстом в `app/(auth)/{dashboard,history,settings/billing}/{loading,error}.tsx` (Stage 13/14) — точный объём дублирования состояний загрузки/ошибки в проекте, зафиксирован числом, не расплывчато.

KISS/YAGNI: ни одной инфраструктуры "на будущее" не найдено — пагинация истории, лимиты, config_schema — везде минимально достаточная реализация под реальную, а не гипотетическую потребность.

### 1.5 Неиспользуемые файлы/компоненты/функции/типы — проверено графом, не grep'ом

Первый (наивный grep) проход по традиции прошлых аудитов дал 2 кандидата — оба разобраны как ложные срабатывания (импорт директории через `index.ts` без явного `/index` в пути). Чтобы не полагаться на это ещё раз, для этой финальной проверки граф импортов построен programmatically и по нему найдены узлы с нулевым числом входящих рёбер.

Результат графового анализа (после исключения Next.js-конвенционных точек входа — `page.tsx`/`layout.tsx`/`loading.tsx`/`error.tsx`/`route.ts`, которые фреймворк использует по имени файла, не по импорту): **один кандидат — `lib/supabase/middleware.ts`.** Проверен вручную: используется корневым `middleware.ts`, который не попал в область сканирования (лежит вне `app/`/`components/`/`lib/`/`config/`). Не мёртвый код — артефакт границ сканирования.

**Итог: ни одного подтверждённого неиспользуемого файла во всём проекте.**

**Неиспользуемые экспорты** (более тонкая проверка — не "импортируется ли файл", а "используется ли каждый его экспорт где-либо ещё"): programmatically проверены все `export function/const/interface/type/class` по всем 146 файлам, с исключением Next.js-конвенционных имён (`GET`/`POST`/`viewport`/`metadata` и т.д. на конвенционных файлах).

**Найдена одна настоящая, ранее не отмеченная находка: `getDefaultProvider()` (`lib/ai-provider/index.ts`, Stage 4) нигде не вызывается.** Функция была написана в Stage 4 как часть публичного API AI Provider Gateway (резолвинг провайдера по умолчанию из `DEFAULT_AI_PROVIDER`), но `lib/generation/pipeline.ts` (Stage 5) реализовал собственную логику выбора провайдера (`selectProviderAndModel`, читает `plan_limits.allowed_ai_models`) и ни разу не обратился к `getDefaultProvider()`. Функция синтаксически корректна, не содержит ошибок, просто не имеет вызывающей стороны. Это не было замечено ни в одном из 14 предыдущих аудитов, потому что каждый из них проверял только новые/изменённые файлы своей стадии плюс общий скан на неиспользуемые **файлы** (не на неиспользуемые **экспорты внутри используемых файлов**) — именно такую более глубокую проверку и запрашивает эта финальная стадия.

Других неиспользуемых типов/интерфейсов не найдено.

### 1.10 Несогласованности между стадиями — включая одну реальную находку

Проверены единые подходы:

- **Supabase-клиенты**: ровно 4 точки создания клиента (`lib/supabase/{client,server,admin,middleware}.ts`); все остальные 8 мест, где встречается импорт `@supabase/supabase-js`, — это исключительно `import type { SupabaseClient }` для типизации параметров, не создание нового клиента. Проверено построчно по каждому вхождению. **Нарушений не найдено.**
- **Server Actions**: ровно 3 файла (`app/login/actions.ts`, `app/register/actions.ts`, `app/(auth)/profile/actions.ts`), все — `"use server"`, все — сигнатура `(prevState, formData) => Promise<{...}>` под `useFormState`. **Нарушений не найдено.**
- **RLS**: все 10 таблиц, созданных в миграциях, имеют `ENABLE ROW LEVEL SECURITY` — сверено 1:1 по списку имён таблиц. **Нарушений не найдено.**
- **Валидация**: `zod` — единственная библиотека, используется в 3 точках (профиль, `/api/generate`, `config_schema`); других систем валидации не подключено. **Нарушений не найдено.**
- **Утечка server-only кода в клиент**: программно проверено — ни один файл с `"use client"` во всём проекте не импортирует ни один модуль, помеченный `"server-only"`. **Нулевой результат подтверждён для всего проекта, не выборочно.**

**App Router — найдена реальная, ранее не задокументированная несогласованность.** Паттерн "серверная страница с реальным Supabase-запросом получает `loading.tsx`+`error.tsx`" был установлен в Stage 7 и последовательно продолжен в Stage 10, 13, 14 — везде, кроме одного места: **`app/(auth)/profile/page.tsx` выполняет ровно такой же асинхронный Supabase-запрос (`requireUser()` + чтение `company_profiles`), что и Dashboard/History/Settings/Tools/Templates, но не получил ни `loading.tsx`, ни `error.tsx`** (Stage 12). Проверено также, что выше по дереву маршрутов (`(auth)/error.tsx`, корневой `app/error.tsx`) никакого перехватывающего error boundary нет — то есть при реальном сбое (например, недоступности Supabase) `/profile` показал бы стандартную, нестилизованную страницу ошибки Next.js вместо оформленного `ErrorState`, а не соответствующий проекту "Loading…"-индикатор при медленном ответе. Это не крах и не баг в смысле неверного поведения — просто единственное отступление от иначе полностью последовательного паттерна, пропущенное во время Stage 12 и не пойманное ни одним последующим точечным аудитом (каждый из них проверял только собственные новые/изменённые файлы, не сверял старые страницы со свежеустановленным паттерном).

**Параллельных архитектурных решений** (два разных способа делать одно и то же) не найдено нигде, кроме двух уже описанных выше, явно принятых компромиссов (§1.4).

## 3. Проверка архитектурной готовности

**Есть ли места, которые необходимо переписать ДО первого запуска?**
Нет. Единственные найденные несовершенства (§1.5, §1.10) — мёртвая функция и отсутствующий `loading.tsx`/`error.tsx` на одной странице — не блокируют компиляцию, не блокируют запуск, не являются архитектурными ошибками. Их можно исправить в любой момент после первого запуска без каскадных последствий.

**Есть ли архитектурные решения, которые являются ошибочными?**
Нет. Каждое значимое решение принималось с явным анализом альтернатив (задокументировано в соответствующем аудите) и минимум дважды проверялось на устойчивость последующими стадиями (например: разделение `lib/generation/catalog.ts` vs `lib/tools/`/`lib/templates/` выдержало пять последующих стадий без единой правки; обобщённость `config_schema`/`ToolRunner` выдержала добавление двух инструментов нулём изменений кода).

**Есть ли решения, которые нарушают принципы проекта?**
Нет системных нарушений. Два принятых компромисса (§1.4) — осознанные, обоснованные, зафиксированные в момент принятия решения, а не тихие отступления от принципов.

**Есть ли критичные технические долги?**
Нет. Полный список некритичных находок — в §1.5, §1.6, §1.10 и §5. Ни одна не мешает первой сборке, первому запуску или дальнейшей разработке.

## 4. Проверка согласованности стадий

Stages 1–14 образуют завершённую, взаимно непротиворечивую систему. Прямые эмпирические подтверждения, а не только заявления:

- **Stage 9** добавил два инструмента, не изменив ни одного файла кода из Stage 6–8 — прямое доказательство того, что архитектура `config_schema`/`ToolRunner`/`resolveDefaultTemplate` была спроектирована верно с первого раза.
- **Stage 11** реализовал перенос гостя без единого изменения клиентского кода Stage 2 (`AuthSyncListener.tsx` уже был написан под контракт, который Stage 11 просто заполнил).

## 6. Проверка готовности к запуску

**Можно ли переходить к первой сборке проекта?** Да — весь код статически непротиворечив (импорты, экспорты, типы, баланс скобок проверены по всему проекту), но сама сборка (`npm install && npm run build`) ни разу не выполнялась ни на одной стадии: в этой среде нет сетевого доступа (подтверждено многократно с Stage 2 — `npm ping` возвращает `403`). Первая сборка — это первое реальное событие, которое ещё не произошло.

**Можно ли запускать приложение?** Технически да, но только после успешной сборки и заполнения `.env.local` — ни один запуск не выполнялся ни разу за весь проект.

**Можно ли применять миграции?** Да, `supabase/schema.sql` + `supabase/seed.sql` готовы к вставке в Supabase SQL Editor (см. `supabase/README.md`) — но ни один SQL-запрос из 15 миграций не выполнялся ни на одной реальной базе данных за весь проект. Единственная проверка — статическая (баланс скобок, валидность JSON внутри SQL, сверка внешних ключей с порядком создания таблиц).

**Можно ли переходить к интеграционному тестированию?** Только после первых трёх пунктов. Ни один HTTP-запрос, ни один вызов Anthropic API, ни один реальный проход гостевого/регистрационного/генерационного сценария не выполнялся.

**Можно ли искать runtime-ошибки?** Да, это и есть следующий логичный шаг — но именно потому, что ни одной строки кода в этом проекте ещё не исполнил реальный JavaScript-движок в браузере или Node.js с установленными зависимостями. Все 14 предыдущих аудитов явно и честно фиксировали это в разделе "Что невозможно проверить" — этот финальный аудит подтверждает, что ситуация не изменилась: весь проект прошёл только статическую проверку.

**Можно ли деплоить тестовую версию?** Только после того, как первая сборка пройдёт успешно локально/в Replit или bolt.new.

**Главный содержательный риск при первой сборке**, который стоит проверить в первую очередь: `lib/supabase/database.types.ts` написан вручную (не сгенерирован `supabase gen types`) и не несёт `Relationships`-метаданных — несколько мест в коде (`lib/generation/plan.ts`, `lib/templates/catalog.ts`, `app/(auth)/history/page.tsx` и его `[id]`-версия) защищены явными приведениями типов именно по этой причине. Это отмечалось в каждом аудите с Stage 3 и остаётся самой конкретной, самой вероятной точкой первого реального расхождения между ожидаемым и фактическим поведением. Прямая рекомендация: сразу после первого применения миграций выполнить `supabase gen types typescript` и сверить с этим файлом, до начала интеграционного тестирования.
