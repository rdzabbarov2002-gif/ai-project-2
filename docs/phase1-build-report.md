## 2. Обнаруженные ошибки

### 2.1 Критичные, подтверждены и исправлены

**a) `@anthropic-ai/sdk` версия `^0.32.1` — не просто устарела, а физически не может подтянуть актуальную версию.**
Реальная текущая версия (проверено `npm`-страницей пакета через веб-поиск): **0.127.0**. Семвер `^0.32.1` — это `>=0.32.1 <0.33.0`; он никогда не разрешится в 0.127.x. `npm install` либо поставит очень старую версию (если 0.32.1 всё ещё резолвится), либо не найдёт её вовсе. Проверено дополнительно: форма вызова `client.messages.create({...})` и способ импорта (`import Anthropic from '@anthropic-ai/sdk'`) в официальном README репозитория **не изменились** — код в `lib/ai-provider/claude.ts` остаётся корректным без единой правки, проблема была только в зафиксированной версии пакета.

**b) `config/settings.ts`'s `defaultAIModel` — `"claude-sonnet-4-6"` — устаревшая модель.**
Подтверждено несколькими источниками (документация Claude Platform, AWS Bedrock, независимые источники): актуальная модель — **`claude-sonnet-5`**, выпущена 30 июня 2026 как прямой апгрейд именно для Claude Sonnet 4.6. Без этого исправления каждый вызов генерации в проекте обращался бы к модели, которая может быть уже недоступна или вести себя не так, как рассчитано.

**c) `@supabase/ssr` версия `^0.4.0` — устарела и, что важнее, использует API, отклоняемый текущей версией пакета.**
Реальная текущая версия: **0.12.7**. Но здесь проблема не только в номере: официальная текущая документация Supabase прямо предписывает — "You MUST use ONLY `getAll` and `setAll`. You MUST NEVER use `get`, `set`, or `remove`" — а код `lib/supabase/server.ts` и `lib/supabase/middleware.ts` использовал именно старую форму (`get`/`set`/`remove`). Если бы я просто обновил версию пакета, не поменяв код, — сборка либо не прошла бы проверку типов, либо (что хуже) прошла бы, но авторизация сломалась бы в рантайме. Это не было заметно ни на одной из 15 предыдущих стадий, потому что ни одна из них не имела доступа для проверки актуального API этого пакета.

### 2.2 Некритичные, зафиксированы, не исправлялись (вне объёма этой фазы)

Три пункта, унаследованные из финального аудита Stage 15 (`getDefaultProvider()` — неиспользуемая функция; `/profile` без `loading.tsx`/`error.tsx`; два устаревших номера стадии в комментариях миграции 0008) — **статус не изменился**. Ни один не блокирует сборку и не является "ошибкой сборки" в смысле этой фазы; трогать их сейчас означало бы заниматься задачами стадии стабилизации (Фаза 4), не первой сборки.

## 4. Совместимость зависимостей — что проверено, а не предположено

- **Next.js 14.2.5 + React 18.3.1 + React DOM 18.3.1** — Next 14.x требует React 18.x (не 19) — совместимая, стабильная пара. Оставлена как есть (см. §5 — сознательное решение не переходить на Next 15/16).
- **TypeScript `^5.5.4`** удовлетворяет заявленному требованию `@anthropic-ai/sdk` ("TypeScript >= 5.0 is supported") — подтверждено тем же фетчем README.
- **`@supabase/supabase-js` `^2.45.0`** — не менялся. Проверено: пакет не пересекал границу мажорной версии (актуальные версии, встреченные в поиске, — 2.85.x/2.112.x, всё ещё 2.x) — диапазон `^2.45.0` корректно разрешится в текущую версию без правки.
- **`zod`, `clsx`, `server-only`** — не исследовались так же глубоко, как два вышеупомянутых: это маленькие, крайне стабильные пакеты, и ни для одного из них не нашлось конкретных признаков breaking-изменений (в отличие от Anthropic SDK и `@supabase/ssr`, где нашлись прямые доказательства). Не стал распылять усилия аудита на пакеты без конкретного сигнала проблемы.

## 5. Архитектурное решение, которое стоит явно объяснить: почему НЕ обновлён Next.js

Рассмотрел это явно. Поиск показал, что Next.js за время разработки этого проекта продвинулся до версии 15, затем 16, и что `cookies()` в Next 15+ стала асинхронной. Решил **не** переходить на Next 15/16 сейчас, по трём причинам:

1. Обновление затронуло бы гораздо больше, чем два файла Supabase-клиентов — потенциально App Router-конвенции, поведение middleware, десятки других деталей, которые я не могу безопасно проверить без реальной сборки.
2. Само по себе оно не требуется для устранения найденных ошибок — `@supabase/ssr`'s требование `getAll`/`setAll` не зависит от версии Next.js (проверено явно: `await cookies()` безопасен даже в Next 14, поскольку `await` над не-Promise-значением — легальная, no-op операция в JS, но сам сдвиг API cookies-объекта — это контракт исключительно `@supabase/ssr`, не Next.js).
3. Это прямо противоречило бы правилу фазы "не менять архитектуру без объективной необходимости" — версия Next.js, зафиксированная в Stage 1, работоспособна и внутренне согласована с остальным кодом при уже внесённых исправлениях.

Это решение, а не откладывание проблемы — исправление `@supabase/ssr` было выполнено полностью и достаточно без обновления Next.js.

Категорически невозможно в этой среде — сеть заблокирована на уровне прокси для bash-инструмента (подтверждено `403` на всех проверенных доменах):

  - Полная проверка типов TypeScript **со всеми реальными типами** пакетов (не только синтаксис, который проверен) — не выполнялась. - **Реальное применение SQL-миграций** к живому Postgres — не выполнялось ни разу за весь проект (нет `psql`, нет локального Postgres-сервера, нет сети до Supabase).

- **Реальное поведение исправленного `getAll`/`setAll`** — исправление основано на официальной документации Supabase и множественных независимых подтверждающих примерах кода, но не проверялось вызовом реального Supabase Auth.

## 8. Реальные риски, остающиеся после этой фазы

1. **`database.types.ts` написан вручную** — самый вероятный источник настоящих (не синтаксических) ошибок TypeScript при первой реальной сборке. Рекомендация не изменилась с прошлых аудитов: выполнить `supabase gen types typescript` сразу после применения схемы, до `npm run build`.
2. **Версии `@anthropic-ai/sdk`/`@supabase/ssr`, зафиксированные сейчас (0.127.0 / 0.12.7), были актуальны на момент проверки веб-поиском в рамках этой фазы** — к моменту, когда пользователь реально выполнит `npm install`, могли выйти более новые версии. Диапазоны `^` позволят подтянуть патчи/минорные версии автоматически в пределах текущей мажорной линии.
3. **Исправление `getAll`/`setAll` основано на документации и найденных примерах, не на реальном запуске** — переход в 12 версий (0.4 → 0.12) мог принести и другие, более мелкие изменения поведения, не всплывшие в проверенных источниках.
4. **ESLint/Next.js lint-конфигурация не проверялась вообще** — `npm run build` в Next.js по умолчанию также прогоняет линтер; возможны предупреждения или ошибки линта, не относящиеся к TypeScript/синтаксису и не обнаружимые ни одним доступным здесь инструментом.
5. Три некритичные находки из Stage 15 (§2.2) остаются как есть.

## 9. Подтверждение

**Сборка не может считаться завершённой в этой фазе** — не из-за проблем в коде проекта, а из-за категорического отсутствия сетевого доступа в этой среде. Это чётко разделено:

**Уже подтверждено (в этой среде):**
- Синтаксическая корректность всех 109 `.ts`/`.tsx`-файлов через настоящий JSX-осведомлённый парсер TypeScript.
- Отсутствие циклических импортов во всём графе проекта.
- Корректность всех внешних ключей и RLS-ссылок во всех 15 SQL-миграций.
- Три реальные, подтверждённые веб-поиском ошибки найдены и исправлены безопасно, локально, без каскадных изменений архитектуры.
- `package.json` синтаксически валиден после правок.

**Требует действий пользователя (в среде с реальной сетью):**
- Выполнить `npm install`.
- Заполнить `.env.local` реальными значениями.
- Создать проект Supabase, применить `supabase/schema.sql` + `supabase/seed.sql`.
- Выполнить `npm run build`.
- Сообщить о любых реальных ошибках сборки — если они появятся, это будет первая настоящая обратная связь, которую этот проект получит за всё время разработки, и она станет отправной точкой для быстрой, точечной донастройки, а не перепроектирования.

**Невозможно проверить в текущей среде:** всё, что требует сети — перечислено полностью и честно в §7.

Работа в рамках этой фазы завершена в том объёме, который был возможен без сети: все статически обнаружимые ошибки найдены и исправлены, ничего не осталось "на будущее" без явной, обоснованной причины. Проект готов к тому, чтобы кто-то с реальным сетевым доступом выполнил фактическую первую сборку — это и есть следующий, ещё не пройденный шаг.
