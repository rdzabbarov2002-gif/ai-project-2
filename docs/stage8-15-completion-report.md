## 2. Этап 1 — исправление подтверждённых ошибок (коммит «Phase 1»)

| Ошибка | Последствие | Исправление |
|---|---|---|
| `database.types.ts` не соответствовал `GenericSchema` supabase-js (нет `Relationships`/`Views`, `interface` вместо `type`) | каждая таблица типизировалась как `never`, около 65 ошибок `tsc`, сборка падала | файл приведён к формату генератора; имена FK сверены с реальной БД |
| `plan.ts`: `limits` мог быть `undefined` | падение страницы при пустом `plan_limits` | тот же fail-closed ответ, что и для остальных ошибок чтения |
| `temperature: 0.7` при модели `claude-sonnet-5` | **каждая генерация** получала 400: у текущих моделей параметры семплинга удалены | провайдер Claude не передаёт `temperature`; пайплайн его не задаёт |
| `max_tokens: 2048` | адаптивное мышление Sonnet 5 расходует тот же бюджет, поэтому ответы могли обрезаться | 8192 |
| Пустой ответ модели (например, `refusal`) | сохранялась пустая генерация и списывался лимит | `AIProviderError` — не сохраняется и не засчитывается |
| `AuthSyncListener` ждал `SIGNED_IN` | после входа через server action или письмо перенос гостевых данных **не запускался** | проверка фактического состояния («есть токен гостя и есть сессия») при загрузке, навигации и `SIGNED_IN`; вызов auth вынесен из колбэка (риск deadlock) |
| Черновик профиля гостя жил только в localStorage | контекст компании для гостя и создание профиля при регистрации не работали | `POST /api/session/draft` (zod, admin-клиент, upsert по `session_token`); `setProfileDraft` синхронизирует черновик с сервером |
| Гостевая сессия создавалась на каждой загрузке страницы | лишний токен и лишний POST merge у каждого вошедшего пользователя | сессия создаётся по требованию (первая генерация или черновик) |
| `/login?next=` | открытый редирект | `lib/safe-redirect.ts`: только пути того же origin |
| Next.js 14.2.5 | известные уязвимости, включая обход middleware CVE-2025-29927 | 14.2.35, последний патч ветки 14 (мажор не меняется) |
| `/api/generate` без `maxDuration` | на Vercel функция обрывается через 10–15 с, раньше ответа модели | `maxDuration = 60` |
| `DEFAULT_AI_PROVIDER` ни на что не влиял | переменная окружения была фиктивной | учитывается при выборе провайдера |
| Копирование в буфер | необработанный reject Promise | обработка ошибки (позже — `CopyButton` с запасным путём) |
| README и `supabase/README` утверждали, что `.env.local` уже существует | вводили в заблуждение при установке | исправлено; в `.gitignore` добавлены `*.tsbuildinfo` и `next-env.d.ts`; закоммичен `package-lock.json` |

## 3. Stage 8–15 — что реализовано

### Stage 8–9 (проверка)
Проверены на реальных данных из БД: формы всех трёх инструментов проходят настоящую zod-схему, каждый `{{placeholder}}` соответствует полю формы, `required_fields` совпадают с обязательными полями, промпты собираются настоящим `buildUserPrompt` без остатков `{{…}}`. Теперь это закреплено в unit-тесте `tests/templates-migrations.test.ts`. Изменения кода не понадобились.

### Stage 10 — Templates Library
- Миграция **0016** (структура):
  - `templates.config_schema` — собственная форма шаблона. Это §12 архитектуры: «config_schema инструмента/шаблона». Без неё платформенный шаблон, например Facebook Ad, показывал бы лишний выбор «Platform».
  - `templates.is_default` с частичным уникальным индексом — явный шаблон по умолчанию. Stage 8 выбирал «самый старый» и прямо предлагал ввести такое понятие. Нужно оно потому, что при выполнении `seed.sql` одной транзакцией у всех строк одинаковый `created_at`, и «самый старый» становится случайным.
  - `plan_limits.premium_templates` — право на премиум-шаблоны как данные, а не условие в коде (§13).
- Миграция **0017** (данные): инструмент `content-generator` («AI Content Writer», доступен на Free) для пяти категорий длинного контента; 17 шаблонов по всем 16 категориям §15 (6 премиальных); явные шаблоны по умолчанию.
- Код:
  - `checkUsage` получил причину `template_not_in_plan`;
  - страница инструмента рендерит форму шаблона, а премиум-шаблон на Free заменяет `PremiumTemplateNotice`;
  - в библиотеке — значок «Pro».

### Stage 11 — регистрация и перенос гостя
- Гостевой лимит — 3 генерации (§8), настраивается через `GUEST_GENERATION_LIMIT`. Применяется на сервере в `resolvePlanLimits` (для гостя это Free-план с ограничением). Отдельный код ошибки `guest_limit_reached`.
- `SignUpPrompt` — модальное окно на нативном `<dialog>` (фокус, Esc, backdrop). Открывается при исчерпании гостевого лимита.
- `ToolRunner`: подсказка о гостевом режиме, CTA «сохранить в историю» под результатом гостя, ссылки на следующий шаг для ошибок лимитов.
- `GuestProfileDraftCard` — краткий профиль гостя (4 поля) с приглашением к полному профилю.

### Stage 12 — профиль и онбординг
- `lib/profile-autofill/fetchWebsite.ts` — загрузка сайта с защитой от SSRF:
  - только http/https на стандартных портах;
  - запрет всех непубличных адресов, включая `169.254.169.254` и IPv4-mapped IPv6;
  - соединение идёт на заранее проверенный IP (защита от DNS rebinding);
  - повторная проверка каждого редиректа, таймаут, лимит размера.
- `extractProfile.ts` — предложения полей через AI Gateway (`getDefaultProvider()`: аудит Stage 15 отмечал его как функцию без вызывающих). Если AI недоступен, используются meta-теги страницы.
- Server action `autofillCompanyProfile` (только для вошедших) и общий компонент `WebsiteAutofill` для формы профиля и мастера.
- `/onboarding` — мастер из трёх шагов через тот же `saveCompanyProfile`. Новые аккаунты попадают туда; при существующем профиле мастер сразу ведёт на Dashboard.
- `/auth/callback` больше не игнорирует ошибку обмена кода. `/profile` получил `loading.tsx` и `error.tsx` (находка §1.10 аудита Stage 15).

### Stage 13 — история, лимиты, тарифы
- Общие чтения:
  - `lib/limits/usageSummary.ts` — используют Dashboard, Billing и страница инструмента;
  - `lib/history/generations.ts` — используют History и Dashboard;
  - `lib/supabase/embed.ts` — нормализация embed-запросов.
- Dashboard: напоминание о профиле, лимит, быстрый доступ к инструментам, последние генерации.
- History:
  - фильтры по инструменту и избранному через GET-форму;
  - звёздочка избранного через server action без клиентского JS (RLS-политика 0008 уже была);
  - «Use these inputs again» ведёт на `?from=<id>`: форма заполняется из `input_params` (§16), чтение ограничено владельцем.
- Billing: сравнение тарифов из `plans`/`plan_limits`; кнопки апгрейда отключены с пометкой «coming soon», так как оплата вне MVP.
- Страница инструмента показывает «осталось N из M» до генерации (§10).

### Stage 14 — UX-полировка
- Токены на CSS-переменных, светлая и тёмная тема без мигания при загрузке, переключатель.
- Все используемые пары цветов проходят WCAG AA в обеих темах. Исправлены три существовавших нарушения: белый на янтарном (2.0:1), `success` (3.2:1), `danger` (4.1:1). Таблица — в `config/design-tokens.md`.
- Навигация по §7: гостю — верхнее меню с постоянной кнопкой «Sign up to save»; пользователю — боковая панель на десктопе и нижние вкладки на мобильном. Есть skip-link и `aria-current`. `getUser()` мемоизирован на время запроса.
- Лендинг вместо заглушки Stage 1.
- Дизайн-система §11: `Badge`, `Skeleton` (во всех состояниях загрузки), `Toast`, `CopyButton` (в том числе в истории).
- `ToolRunner`: форма слева, результат справа, кнопка Regenerate.
- Доступность: подписи связаны с полями во всех формах, `radiogroup`, `aria-invalid`.
- PWA: иконки, на которые ссылался манифест (раньше 404), favicon и apple-icon. Service Worker кэширует только хешированную статику; при отсутствии сети показывается `offline.html`.

### Stage 15 — релиз
- Ограничение частоты `/api/generate` (§17): не более 6 генераций в минуту на пользователя или гостевую сессию. Счёт по `generations.created_at` с существующими индексами, поэтому работает между serverless-инстансами.
- Миграция **0018** — исправление уязвимости, найденной проверкой RLS на реальном стеке: политика «users can update own row» (0003) позволяла **любому пользователю сменить себе тариф** через публичный API. Политика удалена, UPDATE отозван у `anon`/`authenticated`. Приложение таблицу `users` не пишет.
- Vitest: 9 файлов, 137 тестов. CI (`.github/workflows/ci.yml`): lint, typecheck, test, build.
- README, `.env.example` и `supabase/README.md` приведены в соответствие с кодом.

## 4. Архитектурные решения

- **Архитектура не менялась.** Слои (Gateway → pipeline → route), контракт `/api/generate`, RLS-модель, «инструменты и шаблоны — это данные» — всё сохранено. Новые инструмент и шаблоны добавлены исключительно миграциями, без кода.
- **Миграции только добавлялись** (0016–0018); выпущенные 0001–0015 не редактировались. `schema.sql`/`seed.sql` пересобраны побайтно; тест проверяет, что они не разойдутся с миграциями.
- **Право на премиум-шаблоны, шаблон по умолчанию и гостевой лимит — данные или настройка**, а не условия по слагам в коде.
- **Новые модули только там, где появился второй или третий потребитель** (`usageSummary`, `history/generations`, `embed`) или новая ответственность (`profile-autofill`, `rateLimit`, `safe-redirect`). Сервисов-обёрток над CRUD не создано.
- **Интерфейс провайдеров не менялся.** `temperature` остался в контракте Gateway для провайдеров, которые его принимают; Claude его игнорирует.

## 6. Что невозможно проверить в этой среде

- **Реальный вызов Anthropic API.** Ключа нет. Использовался мок Messages API: форма запроса проверена, качество ответов модели — нет.
- **Успешное автозаполнение с реального сайта.** Прямой исходящий трафик серверного кода в песочнице блокируется. Разбор HTML, извлечение и запасной путь покрыты unit-тестами; отказы SSRF проверены в браузере.
- **Письма подтверждения Supabase.** В локальном стеке подтверждение email выключено. Путь с письмом проверен до `/auth/callback`, включая ошибочный код.
- **Продакшн-деплой на Vercel.** Нужен доступ к аккаунту пользователя.

## 7. Остаточные риски и известные ограничения

1. **Next.js 14 вне поддержки.** 14.2.35 — последний выпуск ветки. `npm audit` отмечает advisories, исправленные только в 15/16. Многие касаются неиспользуемых возможностей (`next/image`, rewrites, i18n Pages Router, custom server, Windows), но DoS-advisories для Server Components и Server Actions применимы. Рекомендация — отдельный переход на Next 15/16 (асинхронные `cookies()`/`headers()`); в рамках этой работы мажорное обновление запрещено условиями.
2. **`database.types.ts` по-прежнему рукописный** (теперь в правильном формате). После создания проекта Supabase стоит выполнить `supabase gen types` и сравнить.
3. **Гостевой лимит привязан к токену в localStorage.** Очистив хранилище, гость получит ещё 3 генерации. Ограничение по IP требует изменения схемы и было вне утверждённого плана. Частоту всё равно ограничивает rate limit.
4. **Rate limit считает сохранённые генерации.** Если сохранение не удалось, генерация не учитывается в минутном окне; месячный лимит при этом всё равно списывается.
5. **Нет очистки просроченных `guest_sessions`** (§16 упоминает TTL-очистку): поле `expires_at` продлевается, но ничего не удаляет старые строки.
6. **`plan_limits.max_saved_results`** по-прежнему нигде не применяется.
7. **dev-зависимости** (`vitest`, `eslint-config-next` → `glob`) имеют advisories уровня moderate/high. В продакшн-сборку они не попадают.
