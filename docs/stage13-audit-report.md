## Часть 2 (продолжение). Архитектурные решения

**Не переиспользован `checkUsage()` для отображения.**
Рассмотрено явно. `checkUsage()` отвечает на другой вопрос ("разрешить ли генерацию вот этим конкретным инструментом прямо сейчас") и требует admin-клиент, потому что читает гостевые данные наравне с пользовательскими. Dashboard/Settings задают третий вопрос ("сколько уже использовано в этом периоде, для отображения") — не решение allow/deny, без привязки к `toolSlug`. Более того, `checkUsage()`'s поле `remaining` — это "останется **после** следующей генерации" (`limit - count - 1`), а не "сколько осталось **сейчас**" (`limit - count`) — использование его значения для пассивного отображения дало бы число на единицу меньше правильного. Читаю `usage_counters` напрямую через уже существующую RLS-политику, написанную именно под этот сценарий.

**Не создан общий helper для Dashboard и Settings, несмотря на схожий код.**
Рассмотрено и отклонено по прямому прецеденту Stage 10 (`lib/tools/query.ts` vs `lib/templates/query.ts` — там же было решено не объединять два похожих, но не идентичных потребителя). Здесь то же самое: страницы не идентичны (Settings дополнительно читает `subscriptions`, Dashboard — нет), и общая абстракция для двух расходящихся с самого начала потребителей стала бы преждевременной.

**`UsageCard` — новый файл, но не новый слой.**
Ни `UsageService`, ни `BillingService`, ни любой другой запрещённый паттерн не создан — это один презентационный React-компонент, получающий уже посчитанные данные пропсами, ровно как `ToolCard`/`TemplateCard` в прошлых стадиях.

**Progress bar — инлайн-разметка внутри `UsageCard`, не отдельный `components/ui/ProgressBar.tsx`.**
Единственный потребитель на сегодня — сам `UsageCard`. Создание отдельного UI-примитива ради одного места использования было бы преждевременной абстракцией (YAGNI).

**`SignOutButton` подключён на Dashboard, не на Settings.**
Находка Stage 9 была сформулирована именно про Dashboard ("`app/(auth)/dashboard/page.tsx` remains a Stage 1 placeholder... into which this component was never inserted") — именно там и закрыта. Дублировать кнопку выхода ещё и на Settings не запрошено и не обязательно для этой стадии.

**Ни одного нового `LoadingState`/`ErrorState` презентационного компонента — текст инлайн прямо в `loading.tsx`/`error.tsx`.**
Рассмотрено с учётом того, что в проекте уже есть два почти идентичных набора таких компонентов (`components/tools/gallery/`, `components/templates/`, Stage 7 и Stage 10). Третий и четвёртый набор компаундировали бы уже существующее дублирование, а не решали задачу — вместо этого код-текст вставлен прямо в конвенционные файлы Next.js без отдельного файла-обёртки. Зафиксировано как наблюдение в разделе "Найденные проблемы" ниже, не как то, что нужно исправлять сейчас.

## Почему Stage 14 можно начинать без переписывания Stage 13

Stage 13 не вводит ничего, от чего Stage 14 могло бы architecturally зависеть избирательно: `UsageCard` — самодостаточный презентационный компонент без побочных эффектов, страницы Dashboard/Billing читают данные, ничего не пишут (кроме уже существующего пути выхода через `SignOutButton`, не изменённого). Если Stage 14 когда-либо потребует показать использование где-то ещё (например, счётчик прямо в `ToolRunner`), `UsageCard` уже пригоден для этого без изменений — принимает готовые примитивы (`planSlug`, `used`, `limit`, необязательный `status`), не требуя ничего специфичного для страницы, на которой сейчас используется.
