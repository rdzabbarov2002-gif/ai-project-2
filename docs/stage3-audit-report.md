## 3. Архитектурные решения и почему

**`public.users` как зеркало `auth.users`, а не прямая работа с `auth.users`.**
`auth.users` — служебная схема Supabase, RLS-политики на неё в обычном режиме не вешаются, и не все нужные колонки (`plan_id`) там уместны. Строка в `public.users` создаётся автоматически триггером сразу при регистрации (Stage 2 `signUp()` → `auth.users` → триггер → `public.users`), так что для приложения это просто ещё одна таблица с `id = auth.uid()`.

**`plans`/`plan_limits` созданы раньше `users` (0002 до 0003).**
`users.plan_id` — внешний ключ на `plans(id)`. Порядок миграций отражает реальный граф зависимостей, а не последовательность из ТЗ (там `users` был первым в списке) — создание в порядке "как в списке" привело бы к ошибке `relation "plans" does not exist` при первом же прогоне.

**Триггер `handle_new_user` вынесен в отдельную последнюю миграцию (0009), а не лежит рядом с `users` (0003).**
Тело функции пишет в `public.subscriptions`, которая создаётся только в 0007. PL/pgSQL не проверяет существование таблиц на момент `CREATE FUNCTION` (только на момент вызова), поэтому формально можно было бы разместить триггер и раньше — но это было бы миной замедленного действия: любой реальный сигнал регистрации между применением 0003 и 0007 привёл бы к рантайм-ошибке. Разместив триггер последним, после всех таблиц, которые он трогает, этот сценарий физически невозможен.

**`guest_sessions` — RLS включён, но политик нет вообще (default-deny).**
У гостя нет `auth.uid()` — RLS-политику для него в принципе не на что опереть без обходных путей (например, доверять `session_token`, переданному как обычный параметр запроса, что легко подделать). Решение: полностью закрыть таблицу для `anon`/`authenticated` и обращаться к ней только через `service_role`-ключ из серверного кода (Stage 5 — `/api/generate`, Stage 11 — merge). Тот же принцип применён к `usage_counters` и `subscriptions` (только `SELECT` для владельца, никаких прямых записей с клиента) — иначе пользователь мог бы сам себе накрутить лимиты или статус подписки.

**`generations` — единственная таблица, где authenticated-пользователю разрешены `INSERT`/`UPDATE` напрямую (не только `SELECT`).**
Это осознанное отличие от `guest_sessions`/`usage_counters`: для вошедших пользователей `/api/generate` (Stage 5) сможет писать через обычный серверный клиент, привязанный к сессии (RLS работает как для клиента), а не через `service_role`. Привилегированный ключ нужен только для гостевых запросов, у которых нет `auth.uid()`. Это разделение — прямое применение принципа "минимально необходимые права" к двум разным сценариям одной и той же таблицы.

**`max_company_profiles` сделан nullable (правка внесена уже в процессе, не в первой версии).**
Изначально колонку сделал `not null default 1` — но `config/plans.json` для Enterprise уже описывает `max_company_profiles: "unlimited"`, что по всей остальной схеме лимитов означает `NULL`. Расхождение нашёл и исправил до генерации `schema.sql`, не после — см. §5.

**Seed-данные скопированы из `config/plans.json`/`tools.json`, а не придуманы заново.**
Явно, чтобы два источника (JSON-заглушка Stage 1/2 и реальная БД Stage 3) не разошлись по цифрам лимитов. Пока приложение не переключено на реальные запросы к БД (это случится по мере Stage 5/7/10), оба описывают одни и те же значения намеренно.

**Шаблоны (`templates`) не засеяны.**
В `config/templates.json` уже сейчас 16 категорий, но ни одного реального шаблона — прежде чем добавлять фиктивный текст `prompt_template`, для него нет контента (это Stage 10). Таблица создана, проиндексирована, защищена RLS — просто пуста, и это осознанно.

**`updated_at` + `moddatetime` на каждой таблице.**
Дешево сделать сейчас, дорого добавлять потом (миграция на каждую таблицу задним числом). Стандартное расширение Supabase, а не самописный триггер — меньше риск ошибки в собственном PL/pgSQL коде.

**Ручной `Database` type вместо `supabase gen types`.**
Команда требует подключения к живому проекту и сети — недоступно в этой среде. Написал типы вручную, 1:1 со схемой миграций, и подключил к обоим клиентам (`client.ts`, `server.ts`). В README и в самом файле оставил инструкцию перегенерировать его по-настоящему, как только проект будет создан — и свериться, что ничего не разошлось.

## 5. Что нельзя проверить в текущей среде

- **Реальное применение миграций.** SQL не выполнялся ни на одном живом Postgres/Supabase — сети нет (подтверждено ещё в Stage 2 через `npm ping` → `403`). Проверка — только статическая: баланс скобок и `$$`-блоков в каждом файле (все 10 прошли), построчная сверка каждого `references public.X(id)` с реально существующей и уже созданной на тот момент таблицей `X` (раздел проверен явно, не на словах).
- **Поведение триггера `handle_new_user` на реальной регистрации** — включая сценарий "seed ещё не применён" (функция в этом случае оставит `plan_id = null`, но это не проверено вживую).
- **`supabase gen types typescript` против реальной схемы** — `database.types.ts` написан вручную и может разойтись с фактической БД при опечатке; единственная защита — то, что типы писались построчно по тем же миграциям, а не по памяти.

## Что было сделано вместо этого

- Построчная сверка **каждого** `references public.X` с местом создания `X`, с явной проверкой порядкового номера миграции (раздел "3. Архитектурные решения" фиксирует результат: все ссылки идут только на уже существующие на тот момент таблицы).
- Эвристическая проверка баланса `()`и парных `$$` по каждому SQL-файлу (Python-скрипт, вывод — все 10 файлов `OK`).
- `schema.sql`/`seed.sql` генерируются конкатенацией самих файлов миграций (`cat`), а не переписываются вручную — то есть не могут разойтись с source of truth по определению, только по факту неприменения перегенерации после правки (что и произошло один раз с `max_company_profiles` и было тут же исправлено, см. §4).
- Все затронутые `.ts`-файлы (`database.types.ts`, `client.ts`, `server.ts`, `middleware.ts`) прогнаны через `node --experimental-strip-types --check` — синтаксически корректны.

## 6. Потенциальные риски первой сборки

1. **Порядок выполнения важен.** `schema.sql` должен быть выполнен целиком один раз, затем `seed.sql`. Если прервать выполнение `schema.sql` на середине (например, случайно вставив только часть текста на телефоне) — часть таблиц создастся, часть нет, и повторный запуск всего файла упадёт на `already exists`. Решение при таком сценарии: выполнить `drop schema public cascade; create schema public;` в SQL Editor и запустить `schema.sql` заново с нуля (это единственная деструктивная операция во всей инструкции — в README явно не описана, потому что нужна только при ошибке, а не в штатном сценарии; стоит иметь в виду).
2. **Расширения `pgcrypto`/`moddatetime`** обычно уже разрешены на всех Supabase-проектах, но если используется сильно урезанный тариф/self-hosted инстанс без этих расширений в allow-list, `0001` упадёт первым — это будет видно сразу, до создания единой таблицы.
3. **`database.types.ts` — ручной, не сгенерированный.** Реальный `supabase gen types` может отличаться в мелочах (например, Supabase иногда добавляет служебные поля или иначе типизирует `jsonb` как `Json` union). Рекомендация из README/комментария в файле — перегенерировать по-настоящему, как только проект будет создан, до начала Stage 5, где эти типы впервые пойдут в дело.

## 7. Почему схема готова к Stage 4

AI Provider Gateway (Stage 1) как был интерфейсом без реальных вызовов — так и остаётся; Stage 4 подключает реальный Claude-провайдер и не требует ни одной новой таблицы: `generations.ai_provider`/`ai_model` уже существуют как текстовые поля именно под это. `plan_limits.allowed_ai_models` уже хранит список разрешённых провайдеров per-plan — Stage 4 может сразу читать эти данные (когда дойдёт до реальных Supabase-запросов, начиная с Stage 5), ничего не добавляя в схему задним числом.

**Рекомендация перед Stage 4:** применить `schema.sql` + `seed.sql` к реальному проекту Supabase (Dashboard → SQL Editor, см. `supabase/README.md`) и заполнить `.env.local` — это первая реальная проверка всей БД целиком, и лучше сделать её сейчас, пока Stage 4 не начал писать код, который на неё опирается.
