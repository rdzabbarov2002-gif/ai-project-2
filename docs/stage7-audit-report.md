## 3. Архитектурные решения и почему

**Схема `tools` расширена миграцией — единственное отклонение от "ничего не менять без необходимости", и оно объективно необходимо.**
В таблице `tools` (миграция 0006, Stage 3) не было `description`/`icon`/`category` — Stage 6 (`ToolRunner`) их не использовал и не запрашивал. Stage 7 явно требует эти поля для карточек и категорий — без них задание физически невыполнимо на реальных данных. Добавлено двумя отдельными аддитивными миграциями (0012 — структура, 0013 — данные), а не правкой уже поставленных 0006/0010, той же дисциплиной, что миграция 0011 в Stage 5.

**Новый модуль `lib/tools/`, а не расширение `lib/generation/catalog.ts`.**
`resolveTool()` (Stage 5) отвечает на другой вопрос для другого потребителя: один инструмент по `slug`, для сборки промпта, без `description`/`icon`/`category` — они пайплайну не нужны. `listActiveTools()` отвечает на "какие инструменты сейчас доступны для показа" — другая форма, другой потребитель (галерея). Это не дублирование одной и той же логики под два имени, а две обоснованно раздельные выборки из одной и той же таблицы через одну и ту же RLS-политику (`is_active = true` для anon/authenticated, миграция 0006) — политика переиспользована как единый источник истины о "что считается доступным", сам код запроса — нет, потому что и не должен быть.

**`queryTools()` — единая точка "поиск + фильтр + сортировка", а не три раздельные функции.**
Задание явно требует архитектуру, которая "позволит перенести поиск на сервер без переписывания компонентов". Единая функция с сигнатурой `(tools, params) => tools` — это и есть тот шов: `ToolGallery` вызывает `queryTools(tools, {search, category, sortBy})` сегодня синхронно, в памяти; завтра тот же вызов можно заменить на `await queryToolsOnServer(params)` с той же формой параметров — меняется один файл, ни один компонент интерфейса не трогается.

**Категории выводятся из данных (`deriveCategories`), нигде не перечислены вручную.**
Прямое исполнение требования "если появится новая категория, код менять не должно понадобиться" — `deriveCategories` строит список из фактических значений `category` в уже загруженном каталоге.

**`ToolListItem` не содержит `is_active`.**
Осознанное решение, не пропуск: RLS-политика на `tools` уже гарантирует, что любая строка, дошедшая до `listActiveTools()`, активна по определению — присутствие поля `is_active: true` в каждом объекте провоцировало бы компонент на бессмысленную повторную проверку, которую задание прямо запрещает. Отсутствие поля делает такую проверку архитектурно невозможной, а не просто нежелательной.

**Loading/Error State через встроенные конвенции Next.js (`loading.tsx`/`error.tsx`), а не через клиентский `useState`.**
Страница галереи — серверный компонент, данные загружаются до рендера; `loading.tsx`/`error.tsx` — штатный механизм App Router именно для этого случая, уже использованный проектом единообразно.

**`CategoryFilter` переиспользует `Select` из Stage 6, а не изобретает новый select-компонент.**
Прямое исполнение "используй существующие UI-примитивы" — `components/ui/Select.tsx` создан в прошлой стадии для `SelectField` внутри `ToolRunner`, здесь используется по другому назначению (фильтр, не поле формы), но форма и токены те же, без единого нового класса Tailwind вне уже определённых.

| Проблема | Решение | Была ли необходима именно для Stage 7 |

| В `tools` не хватало `description`/`icon`/`category` | Аддитивная миграция 0012 + бэкофилл в 0013 | Да — без этого задание невыполнимо на реальных данных |
| **Перед упаковкой в `lib/tools/` обнаружены три посторонних файла** (`filter.ts`, `list.ts`, `sort.ts`) с несовместимой формой (`ToolSummary` вместо `ToolListItem`, раздельные `filter.ts`/`sort.ts` вместо единого `query.ts`), нигде не импортированные из уже написанного мной кода этой стадии | Проверено grep'ом по всему дереву — ни один файл проекта на них не ссылается; удалены | Да — их присутствие напрямую нарушало явное требование "источник истины должен быть только один"; два конфликтующих, недокументированных API для одной и той же задачи оставлять было нельзя |

Второй пункт стоит выделить отдельно: это не архитектурное решение прошлой стадии (Stage 6 модуля `lib/tools/` не создавал вообще), а посторонний код, обнаруженный в рабочей директории в процессе этой стадии — я не могу достоверно утверждать, как именно он там оказался. Задание требует не откладывать и не оставлять такие находки "на будущее", если они противоречат явному требованию текущей стадии — удалил сразу, а не оставил как потенциальное улучшение.

- **Работа `loading.tsx`/`error.tsx` как реальных Suspense/Error boundary в браузере** — синтаксически корректны и следуют документированной конвенции Next.js, но не запускались.

- Построчная сверка каждого `@/...`- и относительного импорта с реально существующим файлом — 0 пропусков.

- **Прогон по всему дереву проекта на предмет посторонних файлов** — что и выявило три файла в `lib/tools/`, описанных в §4.

## 7. Потенциальные риски первой сборки

1. **`tools_category_idx` на колонке, которая пока везде `NULL` до применения 0013.** Не риск для сборки: индекс создаётся в 0012 раньше, чем 0013 наполняет данные — порядок специально такой (структура → данные, как и во всех предыдущих парах миграций).
2. **`app/(guest)/tools/error.tsx` — обязательный `"use client"`-компонент по конвенции Next.js.** Если в будущей стадии эту директиву уберут "для единообразия" с соседними серверными файлами, сборка не упадёт сразу, но error boundary перестанет работать по спецификации Next.js.
3. **`lib/tools/` и `lib/generation/` читают одну и ту же таблицу `tools` двумя разными запросами — осознанно (см. §3).** При будущем расширении стоит держать это разделение по потребителю (пайплайн vs галерея), а не унифицировать в одну структуру "на всякий случай".

## 8. Почему Stage 8 можно начинать без переписывания Stage 7

Stage 8 включает первый реальный инструмент (`ad-generator`, `is_active = true`) и заполняет его `config_schema` по формату из Stage 6. Ничего в Stage 7 не должно измениться при этом:
- `listActiveTools()` уже готова вернуть этот инструмент в общем списке в тот момент, когда его `is_active` станет `true` — без единой правки кода, только новой строкой данных;
- `ToolCard`/`ToolGrid`/`EmptyState` уже корректно обрабатывают переход от "ноль активных инструментов" к "один активный инструмент";
- карточка уже ссылается на `/tools/{slug}` — тот же маршрут, что `ToolRunner` (Stage 6) обслуживает с прошлой стадии, без изменений здесь;
- если Stage 8 присвоит `ad-generator` реальную `category`/`description`/`icon`, `deriveCategories()` подхватит новую категорию автоматически, даже если она не совпадёт ни с одной из трёх, засеянных в 0013.
