# Database setup

This schema has never been applied to a live database — every migration
was written and statically verified (syntax, foreign-key ordering, RLS
column references) but not executed. Applying it for the first time is
part of Phase 1 (first build) of this project's launch sequence, and it's
a from-scratch setup: nothing has run before it.

## Option A — Supabase Dashboard SQL Editor (recommended, zero setup)

1. Open your Supabase project at supabase.com in your phone's browser →
   **SQL Editor**.
2. Paste the full contents of `schema.sql`, run it.
3. Paste the full contents of `seed.sql`, run it.
4. Done. Check **Table Editor** — you should see 10 tables (`plans`,
   `plan_limits`, `users`, `company_profiles`, `guest_sessions`, `tools`,
   `templates`, `usage_counters`, `subscriptions`, `generations`), and
   `tools`/`templates` should already have 3 rows each (Ad/Email/Social
   Generator, all `is_active = true`, with one default template apiece).

`schema.sql` and `seed.sql` are generated by concatenating the files in
`migrations/` in order (`0001`–`0015`, all 15 already applied into these
two combined files) — they exist purely so you only have to paste
*twice* instead of fifteen times on a phone keyboard. If the schema
changes later, the individual `migrations/NNNN_*.sql` files are the
source of truth; regenerate the combined files from those, don't
hand-edit `schema.sql`/`seed.sql` directly.

## Option B — Supabase CLI (if working from Replit/bolt.new's shell)

```
npx supabase login
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

`db push` applies every file in `migrations/` in order and records what's
been applied, which Option A doesn't track — worth switching to once the
schema is past this initial setup and starts changing incrementally.

## After running either option

Copy your project's URL, anon key, and service-role key (Project Settings
→ API) into `.env.local` (copy it from `.env.example` at the project
root; it is git-ignored) so the app in `lib/supabase/client.ts` /
`server.ts` / `admin.ts` can connect. Also required at this point:
`ANTHROPIC_API_KEY`, for the AI Provider Gateway (`lib/ai-provider/`) to
actually generate content.

## If you already partially applied an earlier version of this schema

Not the common case at this point (nothing has been applied anywhere
yet), but kept for reference: each stage that touched the database added
exactly one small, additive migration on top of Stage 3's original
schema.

- Already ran through Stage 3? Run `migrations/0011_increment_usage_counter.sql`
  (Stage 5), `migrations/0012_tools_gallery_fields.sql` and
  `migrations/0013_tools_gallery_seed_update.sql` (Stage 7), then
  `migrations/0014_ad_generator_activation.sql` (Stage 8) and
  `migrations/0015_email_and_social_generator_activation.sql` (Stage 9).
- Already ran through Stage 5? Run `migrations/0012_tools_gallery_fields.sql`
  and `migrations/0013_tools_gallery_seed_update.sql`, then
  `migrations/0014_ad_generator_activation.sql` and
  `migrations/0015_email_and_social_generator_activation.sql`.
- Already ran through Stage 7? Run `migrations/0014_ad_generator_activation.sql`
  then `migrations/0015_email_and_social_generator_activation.sql`.
- Already ran through Stage 8? Just run
  `migrations/0015_email_and_social_generator_activation.sql` — it's pure
  data (UPDATE + INSERT), no schema change, same shape as 0014.

Nothing after migration `0015` exists — Stage 10 through 14 (Templates
Library UI, guest merge, Company Profile, Usage/Billing UI, History) were
all built as pure application code or, in one case (Stage 10), a data-only
migration already folded into `0015`'s neighbors above. `0015` is the
last one.
