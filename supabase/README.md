# Database setup

Every migration has been applied end-to-end to a real PostgreSQL 16
instance (with a stand-in for the Supabase-specific `auth` schema and
roles) — `schema.sql` then `seed.sql`, both as separate statements and as
single transactions the way the Supabase SQL Editor runs them, with
`seed.sql` re-run to confirm it's idempotent. The signup trigger, the
usage-counter RPC and its `anon` revoke, and the RLS policies were
exercised there too. Applying it to your own Supabase project is still a
from-scratch setup.

## Local development — Supabase CLI + Docker

`npx supabase start` from the project root runs Postgres, Auth and the
API locally (settings in `config.toml`) and applies every file in
`migrations/`, data included — `seed.sql` is deliberately not run on top
(`[db.seed] enabled = false`), since it only repeats the data migrations.
`npx supabase db reset` rebuilds the local database from scratch. The
root README has the full local setup.

### Checks (run in CI on every pull request)

With the local database running:

- `npx supabase test db` — `tests/rls.test.sql`: RLS on every table, the
  exact privileges the client roles hold, and what an anonymous visitor
  and a signed-in user can and cannot read or change, table by table;
  `tests/account-deletion.test.sql`: deleting an account leaves none of
  its rows in any table.
- `npx supabase db advisors --local` — Supabase's Security and
  Performance Advisors.
- `npm run db:types` — regenerates `lib/supabase/database.types.ts`.
  Run it after every schema change and commit the result; CI fails if
  the committed file doesn't match the migrations.

A new table needs its client privileges granted explicitly (see
`migrations/0019_client_privileges.sql`) and a line in the RLS test —
the test fails until it has both.

The options below are for a hosted Supabase project (staging, prod).

## Option A — Supabase Dashboard SQL Editor (recommended, zero setup)

1. Open your Supabase project at supabase.com in your phone's browser →
   **SQL Editor**.
2. Paste the full contents of `schema.sql`, run it.
3. Paste the full contents of `seed.sql`, run it.
4. Done. Check **Table Editor** — you should see 10 tables (`plans`,
   `plan_limits`, `users`, `company_profiles`, `guest_sessions`, `tools`,
   `templates`, `usage_counters`, `subscriptions`, `generations`), and
   `tools` should have 4 rows (Ad/Email/Social Generator and the Content
   Writer, all `is_active = true`) and `templates` 20 (one explicit
   default per tool plus the category templates, 6 of them Pro-only).

`schema.sql` and `seed.sql` are generated by concatenating the files in
`migrations/` in order (`0001`–`0018`, all 18 already applied into these
two combined files: structural migrations into `schema.sql`, data
migrations into `seed.sql`) — they exist purely so you only have to paste
*twice* instead of eighteen times on a phone keyboard. If the schema
changes later, the individual `migrations/NNNN_*.sql` files are the
source of truth; regenerate the combined files from those, don't
hand-edit `schema.sql`/`seed.sql` directly.

## Option B — Supabase CLI (if working from Replit/bolt.new's shell)

```
npx supabase login
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

`db push` applies every file in `migrations/` in order and records what's
been applied, which Option A doesn't track — worth switching to once the
schema is past this initial setup and starts changing incrementally.

## After running either option

Copy your project's URL, anon key, and service-role key (Project Settings
→ API) into `.env.local` (copy it from `.env.example` at the project
root; it is git-ignored) so the app in `lib/supabase/client.ts` /
`server.ts` / `admin.ts` can connect. Also required at this point:
`ANTHROPIC_API_KEY`, for the AI Provider Gateway (`lib/ai-provider/`) to
actually generate content.

## If you already partially applied an earlier version of this schema

Not the common case at this point (nothing has been applied anywhere
yet), but kept for reference: each stage that touched the database added
exactly one small, additive migration on top of Stage 3's original
schema.

- Already ran through Stage 3? Run `migrations/0011_increment_usage_counter.sql`
  (Stage 5), `migrations/0012_tools_gallery_fields.sql` and
  `migrations/0013_tools_gallery_seed_update.sql` (Stage 7), then
  `migrations/0014_ad_generator_activation.sql` (Stage 8) and
  `migrations/0015_email_and_social_generator_activation.sql` (Stage 9).
- Already ran through Stage 5? Run `migrations/0012_tools_gallery_fields.sql`
  and `migrations/0013_tools_gallery_seed_update.sql`, then
  `migrations/0014_ad_generator_activation.sql` and
  `migrations/0015_email_and_social_generator_activation.sql`.
- Already ran through Stage 7? Run `migrations/0014_ad_generator_activation.sql`
  then `migrations/0015_email_and_social_generator_activation.sql`.
- Already ran through Stage 8? Run
  `migrations/0015_email_and_social_generator_activation.sql` — it's pure
  data (UPDATE + INSERT), no schema change, same shape as 0014.
- Already ran through Stage 9 (i.e. everything up to `0015`)? Run
  `migrations/0016_templates_config_and_premium.sql` (structure:
  `templates.config_schema`, `templates.is_default`,
  `plan_limits.premium_templates`) and then
  `migrations/0017_templates_library_content.sql` (data: the Content
  Writer tool, the category templates, premium flags, explicit
  defaults). Every earlier stage's list above also ends with these two.
- Then, for everyone: `migrations/0018_users_no_client_updates.sql`
  (Stage 15 security fix — without it a signed-in user can change their
  own plan through the public API). Apply it even if you apply nothing
  else.
- Then, for everyone: `migrations/0019_client_privileges.sql` (security:
  client roles keep only the privileges the app uses — without it a
  signed-in user can rewrite or backdate their generations and attach
  them to a guest session) and `migrations/0020_foreign_key_indexes.sql`
  (indexes on three foreign keys), then
  `migrations/0021_generation_usage.sql` (token counts and duration per
  generation) and `migrations/0022_feedback.sql` (the in-app feedback
  form's table).

Stages 11–14 (guest merge, Company Profile, Usage/Billing UI, History)
were built as pure application code on top of these; `0022` is the last
migration.
